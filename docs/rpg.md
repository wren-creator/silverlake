# RPG programs

Silverlake runs RPG IV programs on [rpgle_library](https://github.com/wren-creator/rpgle_library), the same interpreter that runs them from a terminal. A program is a `*PGM` object whose attribute is `RPGLE`. Its source is in the object (`data["source"]`), and so is the DDS of its display file (`data["dspf"]`). `CALL PGM(APPLIB/ADVENTURE)` starts it. Every `EXFMT` becomes a screen on the 5250 until the program ends, and then the menu or command line comes back.

This is the first milestone of the RPG phase. It is a runner, not a compiler.

## What works

- **CALL** of a program you hold `*USE` to, qualified or found through the library list. The seeded programs are `APPLIB/ADVENTURE` (a text adventure) and `APPLIB/SALESRPT` (one screen of calculations), both from rpgle_library's examples. APPLIB is not on a basic profile's library list, so type the library.
- **The screen** lands where the DDS put it. Constants and output fields draw as text, input fields as input. Text that would run off the edge is clipped.
- **Keys.** Enter always goes to the program. A function key goes to it only if the display file names it (`CF03(03)` or `CA03(03)`), the way a real display file works. Any other key is refused where it stands with "Function key not allowed." The program decides when it ends, so F3 means nothing unless the DDS asked for it.
- **Number fields.** A real 5250 keyboard will not let a letter into a numeric field. Ours checks on Enter, says "Field X takes numbers only." and shows the screen again without the program seeing the input.
- **Calls between programs.** `CALL 'APPLIB/SR'` from RPG resolves the program against the caller's library list and authority, so a program you cannot use cannot be reached through one you can. An unqualified name uses the library list, the real behaviour: a program in APPLIB is not found by a profile whose list does not have it. Fixed-form factor 2 holds fourteen characters, so a qualified name needs a short program name or free-form source.
- **Runaway programs.** A program that runs more than 200,000 instructions without showing a screen is stopped with "ended abnormally". The interpreter runs in the server's own thread, so without the cap one `DOW *IN01 = *OFF` would freeze every session.
- **Signing off** with a program on the screen closes it with the session.
- **DSPPGM** shows the two pages captured from the system's own `QCMDEXC`: owner, attribute, type, observable information, **user profile** and **use adopted authority**. Those last two are the reason to look: `*OWNER` means the program runs with its owner's authority.

Source and attributes are saved in the state file like any object, so a student's edits would survive a restart, and `reset.sh` puts the seeds back.

## What IBM's pages say about adopted authority

From two IBM support pages, [Adopted Authority](https://www.ibm.com/support/pages/adopted-authority) and [Using Adopted Authority for the CRTUSRPRF without *SECADM](https://www.ibm.com/support/pages/using-adopted-authority-crtusrprf-without-secadm-special-authority). The adopted authority milestone follows them.

- `USRPRF(*OWNER)` makes the program run "combining the authorities of the Owner of the program with those of the User Profile running the program". The user keeps their own.
- `USEADPAUT(*YES)` means adopt from the *prior program in the call stack*, not from the owner. If B is `USEADPAUT(*YES)` and `USRPRF(*USER)`, whatever A adopted flows to B. `USEADPAUT(*NO)` cuts that off.
- Adopted authority is only there while the program is active, and is suspended if it is interrupted.
- Not covered by adopted authority: system request, the attention key, break handling programs, and debug functions. `TFRGRPJOB` does not pass it to the group job. The IFS does not support it at all.
- When a program adopts to run `CRTUSRPRF` and assigns a group profile, the user still needs `*CHANGE` and `*OBJMGT` to that group profile by their own authority. Adoption does not supply it (a refusal shows as `CPF9802`).
- IBM's advice is to adopt an application owner's authority, not QSECOFR's or any `*ALLOBJ` profile's.

## Adopted authority and QCMDEXC

A `*PGM` with `USRPRF(*OWNER)` adds its owner to whoever called it, for as long as it is on the call stack.

- **What is added.** The owner's object authority and special authorities. The user keeps their own, so the result is the two combined. That the special authorities count is inferred from IBM's pages, not stated, and sits on the verification list.
- **What passes down.** `adopted_owners` in `system/rpg.py` walks the stack outermost first. `USEADPAUT(*YES)` lets a program keep what the one before it held, `*NO` cuts that off, and a program with `USRPRF(*OWNER)` adds its own owner on top.
- **Nothing sticks.** The profile is copied for the duration of the call (`ProfileStore.adopting`) and the copy keeps the user's name. Objects it creates are the user's, as on IBM i. The job log says which owner a program ran as.
- **The one place it does not apply.** Assigning a group profile in `CRTUSRPRF` still needs the user's own `*CHANGE` and `*OBJMGT` to the group (IBM). Silverlake uses the existing "not authorized to user profile" message where a real system shows CPF9802.
- **`CALL 'QCMDEXC'`** is answered inside Silverlake. The command string goes to the same dispatcher the command line uses, as the profile the stack holds right now, and never to a shell. Parameter two is the length and only that many characters are read. An unknown command says "Command X in library *LIBL not found." (captured). A length that cuts a command mid-parenthesis says "A matching parenthesis not found." (captured). A command that works says nothing. A failure ends the program with that message, which is a guess at how a real program sees it, and a command that needs a whole screen (WRKACTJOB, DSPLIBL) is refused, because a program has no screen to give it.
- **The seeded hole.** `APPLIB/RUNCMD` is a support helper owned by QSECOFR, compiled to adopt its owner, that hands whatever is typed to QCMDEXC. STUDENT types `CRTUSRPRF USRPRF(EVIL) PASSWORD(EVIL) USRCLS(*SECOFR)` and the helper makes it. `APPLIB/RUNCMDX` is the fix: a short allow-list, and an owner (QDFTOWN) that holds no special authority, so a hole in the list gives away nothing. Read the source with `DSPPGM` and the `data` of the object, edit it, and watch the difference.

## Files

An RPG program's externally described `DISK` files are `*FILE` objects (attribute PF) that carry their record layout (`dds`, the DDS source) and their `records`. Both seeded files have them: `APPLIB/PAYROLL` (employees, locked down by the PAYAUTL authorization list) and `APPLIB/CUSTOMERS`.

- **Finding the file.** The F-spec name is resolved through the job's library list, the way a program name is. A name that is not there, or a library the user cannot reach, stops the program before it starts.
- **Authority at open.** Opening for input needs `*OBJOPR` and `*READ`, for update also `*UPD`, for output `*OBJOPR` and `*ADD`. After that each READ, WRITE, UPDATE and DELETE is checked for `*READ`, `*ADD`, `*UPD` and `*DLT`. The check uses whoever the call stack holds at that moment, so a program that adopts its owner reaches a file the user cannot, only while it runs, and a program that does not adopt, or that sits under `USEADPAUT(*NO)`, does not. A refusal ends the program with "Not authorized to use object ..." (the wording is ours, see below).
- **Where the data lives.** A run copies the records into a private SQLite database, and what the program writes goes back into the object after each screen and when the program ends, so it survives `./stop.sh` and goes away with `./reset.sh`. Only one file of a given name can be open in a job, because the library keys its tables by name.
- **The seeded lesson.** `PAYLOOK` is owned by OPERATOR, who holds `*USE` on PAYROLL through the list, and adopts its owner: anyone can look an employee up and nobody can change one through it. `PAYADJ` is owned by SECADMIN, who holds `*ALL`, adopts its owner, and checks nothing about who is calling. A basic user who may call it can set anyone's salary. The fix is not in the program: take `*PUBLIC` off the program (`RVKOBJAUT OBJ(APPLIB/PAYADJ) OBJTYPE(*PGM) USER(*PUBLIC) AUT(*USE)`) and grant it to who should have it.

## Logical files

`CRTLF FILE(lib/name) SRCFILE(lib/QDDSSRC) SRCMBR(*FILE)` builds a `*FILE` object (attribute `LF`) that is a re-keyed view over one or more physical files, rather than records of its own. A plain logical file's DDS names its one physical file with the `PFILE` keyword, before the `R` line, the same position `UNIQUE` sits in on a physical file's own DDS, and carries its own `K` lines for the key the logical file reads in; it may add `S`/`O` (select/omit) lines to show only some of that file's records. A join logical file names every physical file it combines with `JFILE` instead, primary first, and gives each secondary's join condition on a `J` line with one or more `JFLD` lines. No field lines are supported: a logical file always shows every field of the file(s) it is built over, in file order.

- **Creating one.** `*USE` on every physical file named by `PFILE`/`JFILE` is needed to compile the logical file at all (checked the same way a program's own F-specs are, through the library list), and the object records which ones it is built over (`data["based_on"]` for the primary, `data["joined"]` for a join's secondaries, both `LIB/NAME`) so they never have to be re-resolved. There is no `records` of its own.
- **Opening one.** An F-spec can name the logical file exactly as it would the physical file. The physical files' own authority is not checked again at open, only at `CRTLF` time: from there, the logical file has its own owner and its own authority, so a profile can be handed read access to PAYROLL through a logical file without ever being granted anything on PAYROLL itself, and a refusal names the logical file, not the physical one ("Not authorized to use object ... type *FILE.").
- **Sharing the data.** A plain logical file's physical file loads once, whichever name opens it first, direct or through a logical file, and is written back to the physical file's own object. Two handles, one through each name, position independently: `SETLL`, `CHAIN`, `READ` and the rest on one do not move the other, the same as two file pointers over one table on a real system.
- **Select/omit.** `S` requires a match, `O` excludes one, each line one `COMP` (`EQ`/`NE`/`GT`/`LT`/`GE`/`LE`), `RANGE` or `VALUES` condition; every S line and every O line is ANDed in. A filtered logical file still shares the physical file's own table and records — it just never shows the rows its conditions exclude.
- **Join logical files.** Built as an inner join (every secondary needs a matching row, or the primary's row does not show either), one secondary joined straight to the primary (a secondary joined to another secondary is not supported), one match per secondary (`JDUPSEQ`, more than one, is rejected). Every field of every joined file shows, so a field name shared by two of them is an error unless it is itself the pair a `JFLD` joins on. A join logical file is read-only: `WRITE`, `UPDATE` and `DELETE` through one all refuse, the same as a real one.
- **Not modeled.** Choosing or renaming individual fields, `DESCEND` keys. A logical file DDS that tries to name a field refuses outright rather than silently showing the wrong thing. None of this is from a capture: it follows how DB2 for i's logical files are documented to behave, and the actual message IDs and screen layout (there is no F4 prompt for `CRTLF` yet) are unconfirmed against a real system.

## Printer files

A program that declares a `PRINTER` file in its F-spec prints through a `*FILE` object with attribute PRTF, which carries the printer DDS (`dds`) and the queue its output goes to (`outq`, `LIB/NAME`, default `QGPL/QPRINT`).

- **Authority.** The printer file needs `*USE`, and the queue needs `*READ` (inferred from IBM's output queue pages, not a captured refusal). Both are checked when the program is loaded, as whoever the call stack holds then. A missing queue stops the program before it prints.
- **The spooled file.** What the program writes becomes a spooled file named for the printer file, on the queue, in the job that ran the program, with the next file number in that job. It belongs to the **user**, never to an owner the program adopts, because the job is the user's. It is updated after every screen and when the program ends, so output survives a program that stops half way, and then WRKSPLF, WRKOUTQ, DSPSPLF and the hold, delete and change options work on it like any other.
- **Who can read it** is the queue's business, which is the lesson. `REGRPT` prints the payroll register to QPRINT, which is `DSPDTA(*YES)`, so a basic user can open the file payroll staff just printed. `REGRPTX` is the same program with a printer file that names `APPLIB/PAYOUTQ`, `DSPDTA(*NO)`: the entry is still listed, the contents are not shown to anyone but the file's owner and users with `*SPLCTL`.
- **Status.** A spooled file a program is still writing to carries status `OPN`, not `RDY`, the same as a real one stays open while the job writing to it is still running; it goes to `RDY` the moment the program ends (normally or on an error), through `Files.close_spool_files()`. Nothing in this model refuses HLDSPLF, RLSSPLF or DLTSPLF against a file that is still OPN, which a real system does.
- Page length is 66 lines and overflow is at line 60, the CRTPRTF defaults, unless `CRTPRTF`'s own `PAGESIZE` or a later `CHGPRTF FILE(name) PAGESIZE(n)` set the file's own page length instead (1-255; `PAGESIZE(*DFT)` on `CHGPRTF` clears the override back to the job's default). `CHGPRTF` also takes `COPIES` (1-255, carried as an attribute of the spooled files the printer file goes on to create -- nothing here actually prints more than once) and `OUTQ`, same authority rule as `CHGPF` on a data file (`*OBJMGT` or `*OBJALTER` on the file, `*EXECUTE` on its library) plus `*READ` on a new `OUTQ`. Not modeled: printer file attributes beyond the queue, page size and copies (form type and the rest), and `OVRPRTF`'s own printer-specific parameters (see "Overrides and QTEMP" below).

## Display files

A program's `WORKSTN` file is a `*FILE` object with attribute DSPF that carries the DDS (`dds`). The F-spec name is looked up through the library list, needs `*USE`, and several programs can name the same file: `RUNCMD` and `RUNCMDX` both open the display file `RUNCMD`, so there is one screen layout to read and one to change. Edit the object's DDS and every program that uses it shows the new screen.

- **A simplification.** After the library list, the program's own library is tried. A real job would fail to open a display file whose library is not on the list, and that would make `CALL APPLIB/ADVENTURE` fail for anyone who had not run ADDLIBLE first. Programs and files that are not on the list otherwise follow the list.
- **Older form.** A program object may still carry its DDS inline in `data["dspf"]`. It is used only when no display file of that name is on the list, so programs made before this change keep working.
- **Seeded.** `SCREEN` (ADVENTURE), `REPORT` (SALESRPT), `EMPINQ` (PAYLOOK), `SALADJ` (PAYADJ) and `RUNCMD`, all in APPLIB. The first two are named after the F-specs in the library's example programs.
- A program with more than one display file gets their record formats merged, since the runtime takes one set.

## Source and compiling

Programs can now be made without editing a seed file. Source lives in source physical files and is compiled with the real command names.

- **Source files and members.** `CRTSRCPF FILE(SCRATCH/QRPGLESRC)` makes a `*FILE` with attribute `PF-SRC` (record length 92 by default, which leaves 80 characters of line). Its `members` hold the lines, a type and a text. A line is the data of a source record, columns 1 to 80 of an RPG or DDS line. `SRCLIB` has `QRPGLESRC` (HELLO) and `QDDSSRC` (HELLOD, CUSTPF) to start from, and anyone may `CRTSRCPF` in a library they can add to. Members are written with STRSEU or PDM (next section), or come from the seed.
- **CRTBNDRPG** `PGM(lib/name) SRCFILE(lib/QRPGLESRC) SRCMBR(*PGM) TEXT(*SRCMBRTXT) USRPRF(*USER) USEADPAUT(*YES)`. It reads the member, parses it with the runtime, checks that every file the program declares exists on the library list, is the right kind and may be used, and makes the `*PGM`. The F4 prompt is in the F4 section below. A program that already exists is replaced: the compiling user becomes the owner and the old public and private authorities are kept, and replacing needs `*OBJEXIST` to the old program. That replacement rule is from memory of IBM's REPLACE(*YES), not a page, and is on the verification list.
- **CRTRPGMOD and CRTPGM**, the two-step compile. `CRTRPGMOD MODULE(lib/name) SRCFILE(lib/QRPGLESRC) SRCMBR(*MODULE) TEXT(*SRCMBRTXT)` runs the exact same check CRTBNDRPG does and prints the same kind of listing, but places a `*MODULE` instead of a `*PGM`; a module by itself does not `CALL`. `CRTPGM PGM(lib/name) MODULE(*PGM) USRPRF(*USER) USEADPAUT(*YES) TEXT(*SRCMBRTXT)` binds one module into a program: it needs `*USE` on the module, copies its source and gives the result the program-level attributes a module does not carry on its own (USRPRF, USEADPAUT), the same as CRTBNDRPG would have set them. `MODULE(*PGM)`, the default, means a module with the same simple name as PGM, found through the library list. Only one module: nothing here models several separately-compiled modules calling each other without re-parsing source, so `MODULE` takes a single name, never a list, the way a real bound program's does. Neither has a captured F4 prompt yet.
- **CRTPF, CRTDSPF and CRTPRTF** `FILE(lib/name) SRCFILE(lib/QDDSSRC) SRCMBR(*FILE)` build a `*FILE` of that kind from a DDS member, checked by the runtime's DDS parsers. A file that exists is not replaced. A file with no source (`SRCFILE(*NONE)`, record length only) is not built. IBM's default for the source file is QDDSSRC, which is what is used here. The captured host showed `*NONE` for CRTDSPF and CRTPRTF, which looks like a local default.
- **The listing.** Every compile prints QSYSPRT to QGPL/QPRINT as the user's spooled file in the job, with the source and the messages. A failed compile makes no object and says "Compilation failed. Program NAME not created in library LIB." (ours).
- **From the real system.** The prompts of the five commands and their defaults, and the one message a compile gives for a member it cannot open: "Unable to open member NOPGM of file QRPGLESRC in library NOSUCH." That wording is used for any member that cannot be opened.
- **Why it matters for the range.** Compiling a program that adopts (`USRPRF(*OWNER)`) makes *you* the owner, so it adopts you and nobody else. The way to get someone else's authority is to replace a program they own, which needs authority to it, or to be handed one. Adoption has to be the owner's decision.

## PDM and the source editor

`STRPDM`, `WRKMBRPDM FILE(lib/file) MBR(name or generic*)`, `WRKOBJPDM LIB(lib)` and `STRSEU SRCFILE(lib/file) SRCMBR(name) TYPE(type) OPTION(2 or 5)` are the way in. Code is in `screens/pdm.py`.

- **STRPDM** draws the captured menu (1 libraries, 2 objects, 3 members, 9 user-defined options). Options 1, 2 and 3 open the captured F4 prompts for WRKLIB, WRKOBJPDM and WRKMBRPDM in turn (the same prompt F4 opens on a command line typed with that name); option 9 (user-defined options) stays unbuilt.
- **Work with Members.** Options 2 edit, 3 copy, 4 delete (with a confirm display, F12 keeps them), 5 browse, 6 print, 7 rename, 8 description, 13 change text and 14 compile. 14 picks the command from the member type: RPGLE to CRTBNDRPG, PF to CRTPF, DSPF to CRTDSPF, PRTF to CRTPRTF, into the source file's library. 6 spools the member's lines to QSYSPRT, a plain listing with no compile run (`source.print_member`). 8 answers on the message line with the member's type, line count, text and last-changed time; it does not open a second display, since nothing here was captured to say what a real one looks like. Options 3, 7 and 13 read their value from the command line. 9 (Save) says it is not available, since no save file or media is modeled. F6 creates a member, Position to scrolls, and a command typed on the line runs.
- **Work with Objects Using PDM** (`pdm.ObjectList`) is its own screen now, not an alias for WRKOBJ: the same PDM-style option column, command line and Position to as Work with Members, over `objlist.work_with_objects`. The numbers reuse exactly what Work with Objects (also ours, not captured) already gives each one, so the same option means the same thing on both screens: 2 opens Edit Object Authority, 3 copies (reading NEWOBJ from the command line, like CRTDUPOBJ), 4 deletes (its own confirm display), 5 opens Display Object Authority, 7 renames (reading the new name from the command line), 8 opens Display Object Description, and 13 changes the text (reading it from the command line). 6 (Print) spools the same fields Display Object Description - Full shows to QSYSPRT (`objlist.print_object`), with no compile run, same shape as Work with Members' own 6. 9 (Save) gives the same "not modeled" wording Work with Members' own 9 already does. 14 (Compile) recompiles a `*PGM` or `*MODULE` from its own recorded SRCFILE/SRCMBR (CRTBNDRPG or CRTRPGMOD, picked by the object's type), or says plainly there is none to recompile from when the object was not built from RPG source (every other object type, since `*FILE` objects created by CRTPF/CRTDSPF/CRTPRTF do not keep their SRCFILE/SRCMBR once placed). 15 to 17 stay not built, the way 15 to 17 already sit unbuilt on Work with Members.
- **The editor** is SEU-shaped. Line commands I, D, C, M, R take a count, DD, CC, MM and RR mark blocks, A and B place a copy or move. The command line takes TOP, BOTTOM, FIND, CHANGE 'old' 'new' [ALL], SAVE, FILE and CANCEL. F3 on a changed member opens the exit display (change or create, member name, text, return to editing). Browse shows the member and changes nothing. F11 is "column shift": real SEU's own name for it is Toggle, and that is exactly what it does, a binary flip rather than a graduated scroll. The default view is always columns 1 to 71; F11 flips to a second view one column narrower, anchored on the file's own last data column instead of its first (`source.width`), so a 100-wide file toggles to columns 31-100 and an 80-wide one (the CRTSRCPF default) toggles to 11-80. Typed data and new lines land at the columns actually in view, not always at column 1.
- **Sequence numbers and dates.** Every line has its own `NNNN.NN` sequence number and a last-changed date, carried with the member (`seqs`/`line_dates` next to `lines`, in `source.put_member`/`seq_and_dates_for`), the same way a real source physical file's record carries them. A legacy member, seeded or saved before this existed, is given sequential whole numbers and its own last-changed date the first time something needs them, not re-synthesized every time. A new line, however it's created (typed into a blank, R, a copy or move landing), gets a number interpolated between its real neighbors, so the lines around it keep theirs; a typed-over line keeps its number and is only dated again. If a gap runs out of room at two decimal places, the whole member is renumbered to whole numbers first, same as real SEU does. The date is tracked but not drawn: there is no captured layout for a date column in this editor's narrow prefix area, so showing one would be a guess.
- **Authority and locks.** Editing needs authority to write the file, browsing only to read it, and a member is locked to one editor at a time (in memory, released at F3 and at sign off).
- **From the real system.** The menu and the refusals: "Library NOSUCH was not found.", "You do not have authority to file QRPGLESRC in LIB.", "Library NOSUCH not found." (STRSEU says it without "was"). The editor's own key line (F3=Exit, F4=Prompt, F5=Refresh, F9=Retrieve, F10=Cursor, F11=Toggle, F16=Repeat find, F17=Repeat change, F24=More keys, no F12 or F23 on it at all) and F11/Toggle's exact behavior, captured live against PUB400: a brand-new empty member stages in the edit session only (WRKMBRPDM showed "No members in file" afterward, un-saved). The Work with Members, Work with Objects and editor layouts, positions and messages otherwise are ours.
- **Known limits.** A typed prefix is read by comparing the field to the sequence number it started as. There are no syntax prompts: real SEU's F4=Prompt only works with the cursor sitting on a data line ("Function key only valid on data line." otherwise, captured), and Silverlake's screens do not carry the terminal's cursor position into `handle()` at all, so that gate cannot be modeled faithfully without a bigger change to the screen model than this one feature calls for. F4 inside the editor still does nothing.

## Overrides and QTEMP

Two ways a caller can change what an adopting program touches, both about what a name means at the moment the program uses it.

- **QTEMP is per job.** Anything made in QTEMP carries the job that made it, only that job can find it (`objects.visible`, which `locate` applies, with the job carried on the search list `Session.search_order()` returns), and it is deleted at sign-off. The library itself is still one shared object, so two jobs cannot both make a `*FILE` of the same name in QTEMP, a simplification that costs nothing on a loopback range with one student. `WRKOBJ`, `WRKOBJOWN` and `CHGOBJD`'s generic-name and `*ALL` match now carry the same `visible()` check, so a QTEMP object from another job doesn't show up in anyone else's list (`objlist.work_with_objects`, `work_with_objects_by_owner`, `change_description`). `DSPOBJD` and `CHGOBJD` on one named object already went through `locate()`, so they were never affected. The default library list puts QTEMP after QGPL and before anything added with `ADDLIBLE ... *LAST`, which is where a site's application library usually goes.
- **OVRDBF, OVRPRTF and DLTOVR.** `OVRDBF FILE(STAFF) TOFILE(APPLIB/PAYROLL)` makes any program that opens STAFF in this job open PAYROLL instead. It needs no authority and is not checked when issued. The open is checked, as whoever the call stack holds, so an adopting program opens the caller's choice with its *owner's* authority. The job log says "File STAFF overridden to APPLIB/PAYROLL." `SECURE(*YES)` protects an override from later overrides (IBM's wording, from the web, not captured). All three OVRSCOPE values act as `*JOB` here, and MBR is ignored. `OVRPRTF FILE(name) TOFILE(lib/name) SECURE(*YES|*NO)` is the same mechanism (`overrides.py`'s one dict, keyed by file name, does not care whether a DISK or a PRINTER F-spec opens it) for a printer file: the program still `WRITE`s to the name its F-spec declares, and that name is what both authority and the resolved object's own output queue follow, same as a DISK override's CHAIN. Not built: an override on a file the program names with EXTFILE, and OVRPRTF's own printer-specific parameters (COPIES, FORMTYPE, PAGESIZE and the rest), which are not accepted at all rather than accepted and ignored, since they would say something this doesn't model.
- **DSPOVR** `FILE(*ALL|name)` shows this job's own overrides; there is no JOB parameter, since a real DSPOVR only ever shows the job it runs in. Captured on PUB400 (`captures/pub400/auth-ovr.json`, a job with no overrides, read-only): the real title is "Display All Merged File Overrides", not "...All File Overrides"; there is no Job/User/Number header, a "Call level" line stands in its place; a "Type options, press Enter." / "5=Display override details   8=Display contributing file overrides" option line sits above the list, though neither option is built; the column header is "Opt  File        Type  Keyword Specifications" with no Level column; and the key line is "F3=Exit   F5=Refresh   F12=Cancel" with no F16. All of that replaces an earlier, uncaptured guess that WRKJOB's own "Display All File Overrides" option used and still does (`screens/worklists.py`'s `overrides_screen`, shared by both paths). The populated rows are ours: File and Keyword Specifications (`TOFILE(...)`, plus `SECURE(*YES)` when set) are filled in; Type is always blank, since nothing here runs more than one override on a file at once for Type or the two options to have anything to say about.
- **Seeded.** `EMPDIR` adopts OPERATOR and reads `STAFF`, a public directory with the same layout as PAYROLL and a zero salary column. A basic user overrides STAFF to PAYROLL and the lookup shows real salaries. `EMPDIRX` is the same code owned by QDFTOWN, which has nothing on PAYROLL, so the redirected open is refused. `PAYRUN` adopts SECADMIN and calls `PAYCALC` by name alone. A basic user compiles their own `PAYCALC` into QTEMP, which is ahead of APPLIB on the list, and PAYRUN runs it with SECADMIN's authority. In the test it grants the user `*USE` on PAYROLL with QCMDEXC. `PAYRUNX` calls `APPLIB/PAYCALC`, so the list cannot choose.
- **Why the fix for EMPDIR is the owner and not an override.** A real RPG program opens its files before its first statement, so it cannot override its own files in time, unless the F-spec says USROPN. The real defenses are a CL driver that overrides with SECURE(*YES) (CL programs are not built here), an owner who can reach only what the program needs, and USROPN with the override first. The seed uses the least-privilege one.
- **USROPN.** An F-spec keyword (fixed-form, in the keyword area, or free-form `dcl-f name disk usropn;`), built in both rpgle_library (the F-spec flag, the `OPEN` and `CLOSE` statements, and `FileRuntime`'s deferred-open table in `fileops.py`) and Silverlake (`Files.open_user_file` in `system/rpg.py`, the host side `OPEN` calls into through `run_program`'s `open_hook`). A USROPN file's record layout still binds at CALL time, the same as any file (a real compiler binds the layout once, before any override can exist), but it is not opened, and no authority is checked, until an `OPEN` statement runs; any other file opcode against it before that raises "File X is not open" instead. `OPEN` re-applies whatever override is active *at that moment*, not whatever was active when the program started, so a program that issues its own `OVRDBF` through `QCMDEXC` after it starts and before its `OPEN` gets the file it just redirected to, not the one the F-spec names. `OPEN` on a file already open, and `CLOSE` on one already closed, do nothing. `CLOSE` on a file that was never USROPN closes it, but nothing reopens it automatically; that needs auto-reopen-on-next-access, not built. Opening a logical file with `OPEN` is not supported yet.

## CPYF, DSPPFM, CHGPF, RGZPFM and CLRPFM

Files can now be copied and read without writing RPG. Code is in `system/dbfiles.py` and `screens/pfm.py`. Nothing here was captured from a real system: the authority each needs is from IBM's pages as remembered and the completion wording and the display layout are ours.

- **CPYF** `FROMFILE(lib/file) TOFILE(lib/file) MBROPT(*NONE|*ADD|*REPLACE|*UPDADD) CRTFILE(*NO|*YES) FROMRCD NBRRCDS FMTOPT(*NONE|*MAP|*NOCHK)`. `*USE` on the from-file, `*OBJOPR` and `*ADD` on the to-file, plus `*DLT` to replace and `*UPD` to update. A to-file that already has records is refused unless MBROPT says what to do. A unique key refuses a duplicate. `FMTOPT(*NONE)` needs the same field names, `*MAP` and `*NOCHK` copy the fields the two share. Source files are refused (CPYSRCF is not built), FROMMBR and TOMBR are accepted and ignored.
- **The lesson.** A file made by CRTFILE(*YES) belongs to the person who copied and gets the library's create authority, so it is not on the original's authorization list. `*USE` on a locked file is enough to leave with a copy nobody locks. In QTEMP the copy leaves no trace after sign-off.
- **CHGPF, RGZPFM and CLRPFM** (`dbfiles.change_physical_file`, `reorganize_member`, `clear_member`), all `FILE(lib/name)`, needing `*OBJMGT` or `*OBJALTER` on the file and `*EXECUTE` on its library (CHGPF's own page, from a web search, not read in full), RGZPFM adding all the data authorities (`*READ *ADD *UPD *DLT`, a forum's quote of its help text, not an IBM page), and CLRPFM adding `*DLT` (IBM's CL reference, again by way of a web search quoting it; refusal is CPF3137). CHGPF's only required parameter is FILE: everything else real CHGPF takes (SIZE, MAXMBRS, REUSEDLT, LVLCHK, ALLOCATE, CONTIG) changes an attribute this minimal PF model does not track, so it is accepted and ignored, and the command exists for its authority check and completion message. RGZPFM compacts the gap a deleted record leaves on a real system; here a DELETE removes the row outright (SQLite, by way of rpgle_library's `Database`), so there is no gap to compact, and RGZPFM is the same: authority and a completion message. CLRPFM is the one with a real effect: it empties the file's records, same object and authority otherwise. None of the three check for an exclusive lock (no one using the file), which the real commands want and this doesn't model.
- **CPYSRCF** `FROMFILE(lib/file) TOFILE(lib/file) FROMMBR(name|*ALL) TOMBR(*FROMMBR|name) MBROPT(*REPLACE|*ADD)` (`source.copy_members`), copying one member, or every member under its own name with `*ALL`, between two source files. Not found on an IBM reference page: a web search turned up only CPYF's own page naming CPYSRCF as the way to copy source members, and a third party's description of what FROMMBR and TOMBR take. The authority check reuses `source.can_write`'s `WRITE`, the same gate STRSEU and PDM's own member edits already go through, since the real authority section was not found. TOMBR naming one member only makes sense with a single FROMMBR; `*ALL` always keeps each member's own name.
- **CPYTOIMPF** `FROMFILE(lib/file) TOFILE('/ifs/path') RCDDLM(*CRLF|*LF|*CR|*LFCR|*EOR) STRDLM(*DBLQUOTE|*NONE)` (`dbfiles.copy_to_import_file`), writing a data file's records as delimited text to an IFS stream file through `ifs.write` (made if it is not there, same as `>`). RCDDLM's and STRDLM's choices are IBM's own (a web search of the command page, not read in full); the delimited line itself, character fields quoted unless STRDLM(*NONE), numbers written plain, fields comma-separated, is ours, since the page's own grammar for it was not found. Needs `*USE` on the from-file; writing the path takes whatever `ifs.write` already takes, not a separate authority of CPYTOIMPF's own.
- **DSPPFM** `FILE(lib/file)` needs `*USE` and shows each record as its raw characters (numbers as zero-filled digits, no decimal point and no sign zone). Control takes a record number, T or B, Roll moves a page, F19 and F20 shift 71 columns (24 bytes in the hex view). F10 switches to a hex view, a pair of rows per record (the bytes in hex above, the same bytes as characters below, 24 to a line so the hex line is 71 columns too); F11 switches back. Find takes a string and jumps to the next record, from the one on top, whose text contains it, case-insensitively; "String 'X' not found." if none do. None of this is captured, since finding a PUB400 file to point DSPPFM at without exploring the host interactively first was more than a read-only screenshot justified; the layout, the hex view's two-rows-per-record shape, and Find's exact wording are ours. Not built: F21 (split) and a member other than the first.

## Record level locking

Built in rpgle_library (`database.py`'s `FileHandle.mode`, `_acquire`, `_release`, `release`, and `Database(lock=..., unlock=...)`) and Silverlake (`Files._lock_record`, `_unlock_record`, `_job_id`, `release_locks` in `system/rpg.py`, and `ProfileStore.record_locks`, memory only like `member_locks`).

- **What locks.** A file opened `U` or `C` (update or combined) locks the record a `CHAIN`, `READ`, `READE`, `READP` or `READPE` positions on; `I` (input-only) never locks anything, so two jobs reading the same file never contend. A logical file opened over the same physical file locks by the physical file's own name, not the logical file's, so a program that reaches a record through two different views still contends with itself and with anyone else.
- **What releases it.** `UPDATE` or `DELETE` on the current record release it immediately (a real system's own rule: writing the record is what the lock was for). Moving to another record, chain, read in any direction, releases whatever this one program's file was holding before locking the new one. The job ending, normally or by abending, releases every lock it still held (`Run._advance` and `Run.close` call `Files.release_locks()` once the run is done, not on every intermediate screen, since a program can sit on a locked record across several screens without the lock going anywhere).
- **A second job's `CHAIN` for update on a locked record is refused**, `RpgleError("...: record is locked by another job")`, surfaced the way any uncaught RPG error is: "Program X ended abnormally: ...". There is no `WAITRCD`-style wait; a real system without one waits up to the job's own wait time and then gives the same kind of refusal (CPF4101, not captured), so refusing immediately is the same outcome without modeling a wait nobody here can see pass.
- **Who "another job" is**, for locking purposes: the signed-on job if there is one (`Session.job.qualified`), or, in a session with none, the Python session object's own identity, so two unconnected test sessions still contend like two real jobs would. This is the same identity `visible()` already uses to scope QTEMP per job.
- **Not modeled:** `WAITRCD` and any actual wait, `UNLOCK` as a distinct opcode (release only happens through UPDATE, DELETE, moving off the record, or the job ending), and locking on a keyed `DELETE` that does not first `CHAIN` or `READ` the record.

## F4 prompts

F4 on the command line (the menu, command entry, PDM) with a command name typed opens its prompt (`screens/prompt.py`), for 72 commands (71 from the captures, plus CRTLIB): the compile and create commands, the user, library, authority, job, spool, message and PDM commands, and the rest of what Silverlake has. Anything already typed fills its fields, F4 with option 14 beside a member in Work with Members prompts the right compile command filled in for that member, and Enter builds a command line from the fields (only what is not the default goes in, a required parameter always does, so the job log reads like something a person typed) and runs it. A command that finished goes back where F4 was pressed, one that was refused stays on the prompt with its message.

Every layout is drawn from `screens/promptspecs.py`, which is generated from read-only PUB400 captures (`auth-pdm`, `auth-prompts-a` to `h`, `auth-prompts-pages`) by `python -m silverlake.oracle.promptspec`. Rerun the generator when a capture is retaken, do not edit the table.

- **From the real system.** The title, rows, labels, columns, lengths and defaults; the Bottom or More... marker and the key lines (29 prompts offer F10, the rest do not), and what F10 shows; required parameters drawn brighter; "Parameter X required." on Enter and on Roll Up while one is empty, with every field of every empty required parameter redrawn in reverse image and the cursor on the first; Roll Up paging a long prompt (WRKSPLF and HLDSPLF have two pages, OVRDBF three); "Already at bottom of area." on the last page; "+ for more values" lines that carry a field; CHGPWD, which has nothing to prompt for and says `No parameters to show; press Enter to run, F3 to exit.`; and the colors ("Type choices" and the key lines blue, titles and the marker white).
- **Checked against the capture.** Each of the 71 prompts, rendered and decoded the way the oracle decodes the host, has the same input fields, attributes and cursor as the real screen, and 69 have the same text and color in every cell. The two that differ are the CRTDSPF and CRTPRTF default below. `python -m silverlake.oracle compare captures/pub400/auth-prompts-b.json --fields-only` replays one of the runs locally and shows only the sign-on screen differing. Roll Down at the top says "Already at top of area." (captured).
- **Ours.** How a refused command reads on the prompt, the wording of "not built" for F9, F11, F14 and for a second F10, Roll Down at the top of the help, and F10 on the help always saying "Wrong cursor position." (the host said it with the cursor in the corner, and this cannot see where a student moved it), and the key line coming back on a second F24 (and being the same line on every prompt, it was only seen on CRTPF), whether a filled-in required parameter is flagged after a refusal (it is not), which page comes up when the missing name is on another one, and the guess that tells a finished command from a refused one when the message has no ID. Where the captured host offered `*NONE` and a blank library for SRCFILE on CRTDSPF and CRTPRTF (which looks like a local setting) the field holds QDDSSRC and `*LIBL`, IBM's default, so Enter works.
- **F10, Additional parameters.** F10 goes straight there with no check of the required names, keeps what was typed, and shows the whole prompt again with the further parameters under an "Additional Parameters" line, on as many pages as the host had (CRTPRTF has eleven, CHGJOB four). Its key lines drop F10. F12 from there leaves the prompt altogether, as it did on the host. CHGSPLFA stops after its first page, because the host would not page it without a real spooled file. The values a change command shows as current (CHGPRF, CHGJOB) are the signed-on profile's here, not the profile the capture was taken with.
- **F24, more keys.** F24 swaps the two key lines for one, `F9=All parameters   F11=Choices   F14=Command string   F24=More keys`, as the host did on CRTPF. F9, F11 and F14 are not captured, so they say they are not built, and so does any other key that is not Enter, Roll, F3, F5, F10, F12 or F24. (Before this, such a key was taken as Enter and ran the command.)
- **F13, How to use this display.** F13 opens a full screen help titled `Prompt Display - Help`, drawn page for page from the capture with the host's colors: the same text for every prompt, 15 pages, `More...` on 1 to 14 and `Bottom` on 15. Roll Up and Roll Down page it, Roll Up past the end says `Already at bottom of area.`, F3 and F12 go back to the prompt with what was typed still in it, and its own F10 (Move to top), F13 (Information Assistant) and F14 (Print help) are not built, F10 saying `Wrong cursor position.` as it did with the cursor in the corner. Nothing is checked first, and CHGPWD's note prompt opens it too.
- **Laid out but refused.** RCDLEN on CRTPF (a file with no source) and SRCSTMF on CRTBNDRPG say they are not built.
- **Refused before any prompt.** F4 on a command the profile may not use says `Not authorized to command X in library *LIBL.` on the line where it was typed and opens nothing, the way PUB400 did for CRTLIB. It is the same check running the command makes (*USE to the `*CMD` object), so locking a command locks its prompt too.
- **CRTLIB's layout is ours.** The host refused it before showing one, so it has LIB, TYPE and TEXT in the columns CRTMSGQ uses and no F10 page. Commands outside the 72 say F4 is not built for them.

## What it is not (yet)

- **Adopted authority and `QCMDEXC` are built** (next section). Not covered: system request, the attention key, break handling programs and debug (nothing here starts one), and `TFRGRPJOB` (not built). The IFS does not support adoption either, and the simulated PASE will have to keep that true.
- **One input per row.** The runtime keys input by screen row, so a second input field on the same row shows as text. Real DDS often has several per row.
- **One display file per program.** The DDS in the object is the program's display file, whatever name the program gives it.

## Function checks and a program dump

An error in a running program (a runaway loop, a divide by zero, a file or program it cannot reach) now ends with the ID a web search turned up for a real function check, `CPF9999` (`messages.function_check`, not a page read in full). The message's own wording is unchanged from before: the screen's one line was already close to 77 columns for some of these causes (the runaway loop's own text alone is 69), so there was no room left to add "Function check" in front of it and keep the real cause visible. The ID is the part that is new.

The other half of a real function check is `QPPGMDMP`, the spooled file IBM's own RPG manual names for a formatted dump (`rpg.dump_program`, also a web search, not a page read in full). Silverlake writes a stand-in there, in the job that was running, with the program, its library and owner, and the runtime's own error text. What a real dump also shows, the statement in error, the call stack and every variable's value, is not there: by the time the exception reaches this far the interpreter has already unwound past all three (`StoreLoader`'s `active` list is restored in a `finally` as the error passes through each `CALL`), so there is nothing honest to show for them, and the dump says so rather than guessing.

## DSPPGMREF and DSPPGM's source fields

`DSPPGMREF PGM(lib/name)` (`rpg.program_references`) needs `*OBJOPR` to the program (from IBM's page, read in full) and lists the `*FILE` objects its F-specs name, each with how it is used (Input, Output, Update or Combined, straight off the F-spec's own usage code). IBM's page says RPGLE programs can also report `*PGM`, `*DTAARA` and `*SRVPGM` references; none of those are built, since nothing here statically scans RPG source for the programs, data areas or service programs it calls, and guessing would be worse than leaving them out. The panel itself is ours: the page describes the content, a list by library with how each file is used, but gives no layout to copy.

`DSPPGM`'s source file, library and member fields, laid out from the start but always blank, now show what `CRTBNDRPG` recorded on the object (`srcfile`, `srcmbr`) when the program came from one. A seeded program with no source file of its own still shows them blank, honestly, since there is nothing to report.

## CHGPGM

`CHGPGM PGM(lib/name) USRPRF(*SAME|*USER|*OWNER) USEADPAUT(*SAME|*YES|*NO) TEXT(*SAME|*BLANK|'text')` (`rpg.change_program`), from IBM's page, read in full, not a capture. `*OBJMGT` and `*USE` to the program are needed for any change at all. Changing `USRPRF` or `USEADPAUT` specifically needs more: the page says "either be the owner of the program or have all object (`*ALLOBJ`) and security administrator (`*SECADM`) special authorities", so owning a program is not, by itself, enough to hand yourself its adopted authority through someone else's. A program in `QSYS` or `QGDDM` is refused outright (`CPF0544`, the one escape message the page actually ties to a named condition; the rest of its list has no wording to quote, so Silverlake's own refusals carry none).

Not modeled: the page's own rule that changing `USRPRF` or `USEADPAUT` requires the program to be re-created, and the warning that other jobs already running the program may fail when it does. Here the change is immediate and nothing re-creates anything, simpler than the real thing and on the verification list. `OPTIMIZE`, `RMVOBS`, `PRFDTA`, `FRCCRT`, `LICOPT`, `NBRTHD`, `TERASPACE` and `STGMDL` are real parameters this does not take at all: none of them map to anything Silverlake tracks.

## Checked on PUB400

Taken read-only on 2026-10-27 (`auth-callpgm`, local capture). Nothing was created, because compiling a program is a write.

- `CALL PGM(NOSUCHPGM)` says **"Program NOSUCHPGM in library *LIBL not found."** Silverlake uses that wording for CALL only. The message ID was not captured, and the one `locate` uses for other commands stays.
- `DSPPGM PGM(QSYS/QCMDEXC)` is two pages (above). The system's own `QCMDEXC` is user profile `*USER`, use adopted authority `*YES`, type OPM, owned by QSYS.

## Needs a real system with a program in a library of its own

Writes, so each needs a human decision first (PUB400 rules: read only):

- Whether a function key the display file never named is refused with a message, or ignored, or raises an error. "Function key not allowed." is ours.
- What a compile error looks like (`CRTBNDRPG` listing, message IDs) and what the compiler produces for a source member.

The Security Reference chapter 5, "Objects that adopt the owner's authority", is the primary source and was not read.
- Whether `CALL` needs `*USE` or `*EXECUTE` to the program (Silverlake uses `*USE`, as it does for menus).
