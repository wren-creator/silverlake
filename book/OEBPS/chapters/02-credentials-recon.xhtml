Session 2: Credentials and Recon

Goal for this session: see how three ordinary habits, a password nobody changed, an account nobody reviewed, and a queue nobody locked down, add up to full access to the system. Nothing here is clever. That is the point, and it is worth sitting with for a moment before you run anything.

2.1 Why This Comes First

Most real incidents on a business system do not start with a clever flaw in the software. They start with somebody signing on, using a profile the system was told to trust, and the system does exactly what it was asked to do from that moment forward. So before anything else, a review of an IBM i has to ask who can sign on, and with what.

You already have the tools for this session from Session 1: WRKUSRPRF, DSPUSRPRF, WRKSPLF, and DSPMSG, plus one new one, DSPPFM, which displays what is actually stored in a physical file. What changes in this session is the question you are asking with them.

2.2 What the Password Rules Actually Allow

Before touching a single profile, look at what the system would even let a password be. These are system values, global settings that apply to every profile at once:

System valueRange settingWhat it controls
QPWDMINLEN1Shortest password allowed
QPWDMAXLEN10Longest password allowed
QPWDRQDDGT0Whether a digit is required (0 means no)
QPWDRQDDIF0How many old passwords are remembered
QMAXSIGN3Bad sign-on attempts before a profile is disabled

A one character minimum, no digit required, no history kept. None of that is an accident of the simulator. Those are settings a lot of real installations ran for years, because changing a system value is a decision somebody has to make on purpose, and nobody made it.

Now look at what sits on top of those loose rules: every seeded profile here has its own name as its password. You confirmed that much by accident in Session 1 when you signed on as STUDENT. It is not an accident that it works, and it is worth asking how far that one habit reaches.

2.3 How Far One Guess Reaches

Sign off, and sign on again as OPERATOR, with the password OPERATOR. It works. Sign off again, and sign on as QSECOFR, the security officer, with the password QSECOFR. That works too, and QSECOFR is the single most powerful profile on the system.

Think for a second about the lockout you tested in Session 1. Three bad attempts disables a profile, and it sounds like a real defense. It is a real defense, against someone wearing a profile down with guess after guess. It offers nothing at all against a password that is simply the account's own name, because that is not a guess in any useful sense, and a profile's name is everywhere: in the owner column of a library list, in a job name on a work list, in the From line of a message. The lockout never gets a chance to matter when the thing it is guarding against was never the risk.

You are signed on as QSECOFR now. A profile this powerful has spooled output like anyone else, including a log of its own interactive session, called a job log. List it:

WRKSPLF
                          Work with All Spooled Files

 Type options, press Enter.
   1=Send   2=Change   3=Hold   4=Delete   5=Display   6=Release   7=Messages
   8=Attributes        9=Work with printing status

                              Device or                     Total     Cur
 Opt  File        User        Queue       User Data   Sts   Pages    Page  Copy
  _   QPJOBLOG    QSECOFR     QEZJOBLOG   QPADEV0001  RDY       1             1

Type 5 next to it and press Enter. A job log is a record of what happened in a session: the commands typed, the messages the system gave back, and when. Read it the way you would read anyone's command history, which is to say, closely. People type things at a command line they would not say out loud, references to other systems, notes to themselves, the occasional thing that should never have been typed anywhere a log could keep it. Somewhere in this one is a reference to a piece of paperwork behind a change that was made. Find it, and you have your first concrete answer to "what does a weak password on the security officer actually cost."

What a defender checks: which profiles still have a password equal to the profile name, whether the password system values are set to anything meaningful, and who besides the account itself is able to read a job log for a powerful profile.

2.4 The Profile That Looks Smaller Than It Is

A guessable password gets someone in. The next question is what is waiting once they are in, and the honest answer on a lot of real systems is: more than it looks like at a glance. Still signed on as QSECOFR, list every profile:

WRKUSRPRF

As STUDENT in Session 1 this list showed one row. As QSECOFR it shows every profile on the system, and the Text column is where whoever set each one up left a note for later. A few of those notes are warnings that were written down and then never acted on. Look closely at SVCACCT:

DSPUSRPRF SVCACCT
                          Display User Profile - Basic

  User profile .................. : SVCACCT
  Status ........................ : *ENABLED
  Password ...................... : set
  User class .................... : *USER
  Special authority from ........ : explicit
  Special authorities ........... : *ALLOBJ
  Group profile ................. : *NONE
  Owner ......................... : SECADMIN
  Text .......................... : Service account with *ALLOBJ it does not
                                    need.

Read the User class line and the Special authorities line as two separate questions, because they are. User class *USER is the ordinary, powerless default, the same class STUDENT holds. If a review stopped at that line, SVCACCT would look unremarkable. But special authority is given separately from class, one authority at a time, and this account was given *ALLOBJ explicitly, by someone, at some point, for some reason the Text field no longer explains.

*ALLOBJ means exactly what it says: every object authority check on the system passes, for this profile, without exception. Not most objects. All of them. Sign on as SVCACCT, the password is again the profile's own name, and read something that was supposed to exclude everyone:

DSPPFM FILE(APPLIB/VAULT)
                      Display Physical File Member
 File  . . . . . . :   VAULT        Library . . . . :   APPLIB
 .........1.........2.........3.........4.........5.........6.........7.
FLAG{...}
****************** End of Data ******************

Nothing about SVCACCT's own authority entries let that happen. The object itself may well say no one, by name, may read it. *ALLOBJ does not ask the object's opinion.

What a defender checks: every profile's special authorities, not just its user class, with particular attention to service accounts and anything described in its own text as a leftover. An account that nobody remembers the purpose of is an account nobody is watching.

2.5 A Queue That Tells You Who Is Doing What

The last lesson in this session needs no special account at all. Sign off, and sign back on as the ordinary profile you started Session 1 with, STUDENT. Every system keeps an operator's message queue for events worth someone's attention, and on this range it is QSYSOPR. Check who may read it before you try:

DSPOBJAUT OBJ(QSYS/QSYSOPR) OBJTYPE(*MSGQ)
                            Display Object Authority

 Object . . . . . . . :   QSYSOPR         Owner  . . . . . . . :   QSYS

                          Object
 User        Group       Authority
 *PUBLIC                 *CHANGE

*PUBLIC holds *CHANGE, meaning anyone, including an ordinary profile with nothing special about it, can read and add to this queue. Read it:

DSPMSG MSGQ(QSYSOPR)

What comes back is a mix of routine system noise, a job queue wrapped here, a session ended there, and lines someone actually typed to another person through the queue, because that is what a message queue is for. Read every line. A queue like this tells an outsider who is running what, which accounts are active, and when, which on its own is useful reconnaissance. Occasionally it tells them more than that, because people treat an internal message queue as a private channel and type things into it they would never put somewhere they expected a stranger to read.

What a defender checks: the public authority on every message queue that privileged accounts use, and a plain reminder to anyone with access to one that "internal" and "secret" are not the same property.

2.6 What to Carry Into Session 3

Keep three things from this session as you move on. First, a password policy only matters if the passwords it governs were ever changed to begin with. Second, user class is a starting point for a review, not the end of one; special authority is where the real power often hides, one explicit grant at a time. Third, "who can read this" is a question worth asking about every object on a system, not just the ones that are obviously sensitive, because a queue that looks like plumbing is still a place people type things.
