Silverlake 101

A Hands-On Training Syllabus for the Silverlake IBM i Security Range

By Britley Hoff

2026 Edition

Nobody hands a new hire a production IBM i and says go ahead, see what breaks. The machine running payroll does not get opened up so someone can learn what a bad password actually costs. That is a sound rule, and it is also why most people who end up defending these systems learn the hard way, one incident at a time, and most people who are asked to review one have never had supervised time on a real one at all.

Silverlake exists to close that gap without touching anything real. It is a behavioral simulator, written clean room: no IBM code, no IBM media, nothing booted from a licensed image. It speaks 5250 to a real terminal client, answers the way an IBM i answers, and carries the same kinds of weak points a real one carries, a password that matches the profile name, a service account holding authority it never needed, a program that borrows its owner's power and does not check what it is handed. None of it is simulated hard enough to be mistaken for the real operating system, and none of it needs to be. What it needs to teach is the thinking, and the thinking transfers.

This is a five session course, matched to the lessons documented in the project itself. Sessions 1 through 4 are the attack half, run against the range in the state it starts in. Session 5 is the defense half: flip each weakness to its fixed state, run the same steps again, and write down exactly where they stop working. Every screen quoted in this book came from the range itself, run before this book went to print, not described from memory or copied from a manual.

The One Rule That Matters

Test only systems you own or have written permission to test. Everything in this book works on a real IBM i, which is exactly why the rule has to come first and come once, before anything else. Silverlake is the place to build the habits and ask the questions. It is not permission to point either one at a system that is not yours.

Bringing the Range Up

Silverlake needs Python 3.12 or newer and about 200 MB of disk, nothing else, no Docker and no IBM media:

git clone https://github.com/wren-creator/silverlake
cd silverlake
./setup.sh      # makes a venv and installs
./start.sh      # listens on 127.0.0.1:5250
./status.sh     # confirms it's up, and loopback only

It binds to 127.0.0.1 by default and refuses to start any other way. A deliberately vulnerable IBM i has no business being reachable from anywhere but the machine running it. A classroom reaching it over a private network is the one documented exception, and it takes an explicit opt in on the instructor's side, not a setting a student can flip by accident.

Connect with any 5250 client, for example tn5250 127.0.0.1:5250, and sign on. Every seeded profile you will meet in this book, and what it is for, is listed here so you are not guessing later:

ProfilePasswordWhat it is
STUDENTSTUDENTAn ordinary user, no special authority. Where most of this book starts.
OPERATOROPERATORSystem operator, *JOBCTL and more by class.
QSECOFRQSECOFRThe security officer. Every special authority the system has.
SVCACCTSVCACCTA service account holding *ALLOBJ it was never meant to need.
CLERKCLERKLimited capabilities, locked to one menu. The menu has a way out.
DEVELOPERDEVELOPERA programmer profile, owns some of the application's spooled output.

Reset the range to its starting state at any point with ./reset.sh. It is quick, and there is no reason to be careful with a range built to be broken.

When you reach Session 5, two more commands matter: ./scenario.sh list shows every lesson and whether it is fixed, and ./check-flags.sh submission.txt scores what you found against the one secret made for your own machine. Both are explained in full when you get there.

What This Book Will Not Pretend

Silverlake has edges, and this book says where they are instead of writing around them. There is no machine interface, no real DB2 for i, no native program binding, no real printers or tape. What exists is what the lessons in this book need, nothing chased for its own sake. If a screen in front of you ever disagrees with a screen in this book, that is worth writing down and sending to the project. The range gets better because people who use it say what they found.
