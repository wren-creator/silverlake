Session 4: Programs and the Library List

Goal for this session: see what happens when a program borrows someone else's authority and does not check carefully what it is handed, or does not check carefully where the thing it calls actually comes from. This is the session where an ordinary profile ends up with power nobody meant to give it, and it is worth slowing down for, because the mechanism underneath each lesson here is the same mechanism behind a large share of real IBM i findings.

4.1 Adopted Authority, in One Paragraph

A program can be written to run with its owner's authority instead of its caller's, a feature called adopted authority. The idea is reasonable: a clerk should be able to run a payroll report without being given direct access to the payroll file, so the report program adopts an owner who has that access, and the clerk's own profile never needs it. The feature is not the problem. The problem is always the same question, asked and not asked: what does this program let the caller choose, and does the owner's authority follow that choice anywhere it shouldn't?

Four programs in APPLIB answer that question four different ways. You are signed on as STUDENT for all of them. Add the application library to your list first, since it does not come with MAIN's default list:

ADDLIBLE APPLIB

4.2 A Directory Program That Opens a File by Name

Look at the staff directory program before running it:

DSPOBJAUT OBJ(APPLIB/EMPDIR) OBJTYPE(*PGM)

EMPDIR is owned by OPERATOR, and Text on the object list told you it adopts that owner. Run it and look up an ordinary employee number:

CALL PGM(APPLIB/EMPDIR)
                             PAYROLL LOOKUP

 Employee number: 10099

 Name:
 Department:
 Salary:          0000000

                       No such employee

Nothing there yet, because that employee number is not in the file EMPDIR actually reads, called STAFF. Here is the detail that matters: EMPDIR opens STAFF by its bare name. It does not say which library, and it trusts that whatever is open under that name when it runs is the right thing.

OVRDBF, Override Database File, changes what a bare file name means for the rest of the job, and it needs no authority to the file it points at, only to run the command. Point STAFF at the payroll file instead:

OVRDBF FILE(STAFF) TOFILE(APPLIB/PAYROLL)

Run EMPDIR again and look up the same employee number:

                             PAYROLL LOOKUP

 Employee number: 10099

 Name:            FLAG{...}
 Department:      AUDT
 Salary:          0000001

EMPDIR opened the name STAFF exactly as it was told to, found your override instead, and read it with OPERATOR's authority, the authority that can open PAYROLL. STUDENT never touched that file directly. STUDENT redirected what a trusted program believed it was opening, and the program's adopted authority did the rest. Sign off or run DLTOVR FILE(STAFF) when you are done, since the override follows your job, not the file.

What a defender checks: whether a program that adopts authority opens its files by qualified name, LIBRARY/FILE, which a caller's override cannot redirect, or by a bare name, which it can.

4.3 A Program With No Opinion About Who Is Asking

Check the next one before running it:

DSPOBJAUT OBJ(APPLIB/PAYADJ) OBJTYPE(*PGM)

PAYADJ is owned by SECADMIN and *PUBLIC holds *USE on the program itself, meaning any profile may call it. Run it:

CALL PGM(APPLIB/PAYADJ)
                          PAYROLL SALARY ADJUST

 Employee number: 10004
 New salary:      0099999

 Name:            Dunn, Kevin
 Salary now:      0099999

                       Salary changed

Enter an employee number and a new figure, and the screen confirms the change as soon as you press Enter. PAYADJ adopts an owner who holds authority on the payroll file, and the program itself asks nothing about who is calling or whether this particular change makes sense. Every check that matters, who may update a salary, lives entirely in SECADMIN's authority, which STUDENT never held and now effectively has, one field at a time, for exactly as long as this program is running.

Compare this to EMPDIR. There the problem was a redirect the program never expected. Here the program is doing exactly what it was written to do, for exactly the caller it was written to serve, and that is the whole weakness: it was written to serve any caller.

What a defender checks: what a program that adopts authority actually lets its caller do, not just what authority it was given. A program that updates one field with no further check is as strong as its weakest caller, not its owner's good judgment.

4.4 The Library List Decides Which Program Runs

This one needs Session 1's library list, so look at it again before you start. PAYRUN adopts its owner and, inside itself, calls another program named PAYCALC, by name alone, with no library in front of it. When a called program is named that way, the system finds it the same way it finds anything else named bare: by searching the library list, top to bottom, first match wins.

Every job has its own QTEMP, a library that exists only for that job and disappears when the job ends. Crucially, QTEMP sits at a fixed point near the top of the list, ahead of anything you add with ADDLIBLE ... *LAST. Add APPLIB to the end of your list, the ordinary way:

ADDLIBLE APPLIB *LAST

Confirm you cannot read the payroll file yet:

DSPOBJAUT OBJ(APPLIB/PAYROLL) OBJTYPE(*FILE)
Not authorized to use object PAYROLL in library APPLIB type *FILE.

Now put your own program named PAYCALC in QTEMP. This needs the source tools from Session 1's neighborhood, PDM and a compile command, which Session 1 did not cover in depth, so take it a step at a time. First, a source file to hold the member:

CRTSRCPF FILE(QTEMP/QRPGLESRC)

Open it in the editor, STRSEU, or WRKMBRPDM FILE(QTEMP/QRPGLESRC) and add a member called PAYCALC, type RPGLE. The body does not need to calculate a real pay period. It only needs to do one thing while it is running with whatever authority called it:

     D c1              S             25    INZ('GRTOBJAUT APPLIB/PAYROLL ')
     D c2              S             18    INZ('*FILE STUDENT *USE')
     D cl              S             80
     D len             S             15  0 INZ(43)
     C                   EVAL      cl = c1 + c2
     C                   CALL      'QCMDEXC'
     C                   PARM                    cl
     C                   PARM                    len
     C                   EVAL      *inlr = *on
     C                   RETURN

That builds the command GRTOBJAUT APPLIB/PAYROLL *FILE STUDENT *USE as text and hands it to QCMDEXC, the system program that runs a CL command string. Whatever authority is running this code is the authority that command runs with. Compile it into QTEMP:

CRTBNDRPG PGM(QTEMP/PAYCALC) SRCFILE(QTEMP/QRPGLESRC)
Program PAYCALC placed in library QTEMP.

Now call the real program:

CALL PGM(PAYRUN)

PAYRUN runs, adopts its own owner as it was written to, reaches the point where it calls PAYCALC by bare name, searches your library list, and finds yours in QTEMP before it ever reaches the real one in APPLIB. Your code runs with PAYRUN's adopted authority, and the one line it was built to run grants you authority on the payroll file. Check it:

DSPOBJAUT OBJ(APPLIB/PAYROLL) OBJTYPE(*FILE)

STUDENT now appears in the authority list, with *USE, and nobody with the power to grant it did so on purpose. The program you wrote vanishes at sign-off, because QTEMP goes with the job, but the grant it made does not; that authority stays on the object until someone takes it back.

What a defender checks: whether a privileged program calls what it needs by full name, LIBRARY/PROGRAM, which a library list cannot redirect, or by a bare name, and whether anything in the job's library list, especially QTEMP, sits ahead of a library a caller cannot write to.

4.5 A Helper With No Memory of What It Was For

The last one is the simplest to run and the hardest to overstate. Check it first:

DSPOBJAUT OBJ(APPLIB/RUNCMD) OBJTYPE(*PGM)

RUNCMD is owned by QSECOFR, the security officer, holder of every special authority on the system, and *PUBLIC has *USE on the program. Run it:

CALL PGM(APPLIB/RUNCMD)
                             COMMAND HELPER

 Type a command and press Enter.

 Command:
 ______________________________________________________________________

Read that screen for what it actually is: a blank field, in front of a program that adopts the security officer, that will hand whatever you type straight to QCMDEXC. There is no narrower version of this weakness to describe, because the program does not narrow anything. It was written, presumably, to save someone a trip to a command line for one routine task, and it was never taught the difference between that task and any other command the security officer could type.

What you can do here is exactly as wide as what QSECOFR can do. That includes creating a profile with every special authority this system has, which is the single clearest proof that adopted authority, handed to a program with no checks, is not a smaller version of the owner's power. It is the owner's power, full stop, for as long as the program is willing to run what it is given.

What a defender checks: every program on the system that adopts an owner and also, anywhere in its logic, passes a string built from user input to QCMDEXC or runs a command the caller supplies. That combination, adoption plus an unchecked command string, is worth finding before someone else does.

4.6 What All Four Have in Common

Step back and look at the four programs side by side. None of them is broken in the way a crashing program is broken. Each one runs correctly, does what it was written to do, and produces the wrong result anyway, because "correct" was defined too loosely. EMPDIR correctly opens whatever STAFF currently means. PAYADJ correctly changes the salary it is told to change. PAYRUN correctly calls the program its library list hands it. RUNCMD correctly runs the command it is given. Every one of them is a program doing its job. The authority behind that job is the part nobody narrowed.

4.7 Take-Home: Read the Fix Before You See It

For each of the four programs, write one sentence predicting what a fix would have to change, without looking ahead to Session 5. Not "make it secure", the specific thing: a bare name that should be qualified, a check that should exist and does not, a call that should name its library, a power that should never have been adopted at all. You will find out in Session 5 whether you were right, and being wrong is as useful here as being right, because it tells you which mechanism you have not quite pinned down yet.
