Session 5: Fix and Re-Run

Goal for this session: close every weakness you found in Sessions 2 through 4, prove each one is closed by running the same steps again, and write down exactly where each one stops working. Finding a problem is half the job. A finding with no fix and no proof is a complaint.

5.1 Same Range, Other State

Silverlake has two states for every lesson. In the vulnerable state, which is how the range starts, the weakness is there. In the secure state, the setting, authority or object that made the weakness possible has been changed, and nothing else has. Each lesson is a short list of settings with a vulnerable value and a secure value for each, so flipping a lesson is a precise, repeatable change and not a vague "hardening".

That shapes how you think about fixing. You are not looking for a switch labelled "make it safe". You are looking for the specific thing that made each exploit work, and the exercise is to name it. This book will not tell you the fix for each lesson. The system will, if you ask it the right way, and the rest of this session is about asking.

5.2 Three Ways to Change a Lesson

From the shell: scenario.sh

On the machine running the range:

./scenario.sh list                       # the lessons and which are fixed
./scenario.sh set LESSON secure          # fix one
./scenario.sh set LESSON vulnerable      # put one back
./scenario.sh reset LESSON               # vulnerable again, with what an exploit left behind cleared
./scenario.sh mode secure                # the whole range at once

Know what these do before you run them. They stop the server, change the saved state and start it again, so everyone who is signed on is signed off. That is fine on your own machine and rude in a classroom, so say so first.

From a command line: SLSCENARIO

The security officer can change a lesson on the running range with no restart and nobody signed off. Sign on as QSECOFR and type:

SLSCENARIO ID(LESSON) STATE(*SECURE)

The states are *SECURE, *VULNERABLE, *RESET and *LIST, and ID(*ALL) means every lesson. *LIST shows where the whole range stands, with the lesson group, its id and its title. Press F4 on the command for a prompt.

From the menu

Option 6 on the main menu opens Lesson Control, a short menu that lists the lessons and moves the whole range. Every option runs SLSCENARIO, so only the security officer gets anywhere with it. Sign on as STUDENT and try one, and the refusal is a small reminder that a menu is only a list of commands with numbers in front of them.

5.3 The Instructor Leaves a Trail

Every change made with SLSCENARIO leaves a line on the operator's message queue, QSYSOPR:

SLSCENARIO: QSECOFR set qsysopr-recon to *SECURE.

This is on purpose. A real administrator changing a security setting should leave a record someone else can read, and the people who need to read it are exactly the ones who would notice something odd. If you can read QSYSOPR, check it after a change and find your line. A refused attempt, from a profile that is not allowed, leaves nothing.

5.4 The Loop

For each lesson from Sessions 2 through 4, do the same five steps, in this order:

  1. Run it vulnerable. Run the exploit steps and keep the evidence: the screen, the message, the line of output.
  2. Name the mechanism. Before you change anything, write one sentence saying what made it work. Not "the password was weak" but what, precisely, let that one thing lead to the next.
  3. Flip it. Set that one lesson to secure, and only that lesson.
  4. Run it again. The same steps, the same profile. Record where it stops, and what the system said when it did.
  5. Put it back. Reset the lesson so the next one starts from a known state.

One lesson at a time matters because lessons tangle. Fixing the default passwords changes passwords that later lessons sign on with, so a student who flips everything at once loses the way into the next exploit and cannot tell which fix stopped which step. Flip one, test one, reset one.

A worked example

Take Lesson 3, the operator's message queue. As STUDENT, in the vulnerable state, DSPMSG MSGQ(QSYSOPR) shows the queue. Now sign on as QSECOFR and run:

SLSCENARIO ID(qsysopr-recon) STATE(*SECURE)
qsysopr-recon: now secure.

Run the same command as STUDENT again:

DSPMSG MSGQ(QSYSOPR)
Not authorized to message queue QSYSOPR.

That is where it stops, and the message says which check stopped it. Your write-up for this lesson records the command, the profile, the message, and, from Session 1, the command that shows why: DSPOBJAUT OBJ(QSYS/QSYSOPR) OBJTYPE(*MSGQ) before and after. Compare what it showed you in each state and you have named the mechanism without anyone telling you.

Notice what did not change. QSECOFR can still read the queue. The fix did not take the queue away from the people who need it. It stopped everyone else from reading it, which is what a good fix does.

5.5 Reading Where It Stops

Different lessons stop in different ways, and part of the skill is recognising which kind of stop you are looking at. In your write-up, classify each one:

What you seeWhat it tells you
A refused sign-onThe credential no longer works. The fix is on the profile or its password.
A Not authorized messageAn authority check now says no. Find which object, and which layer: library, object or special authority.
An empty list or a missing objectThe system filtered what you may see, or the object is not where it was. An empty screen is not an empty system.
The program runs, but does lessThe code now uses a different authority or name than it did. Read the program's description and its owner again.
A different flag, or no flagThe data moved or changed. Check that you did not break your own test.

5.6 Naming the Mechanism

The word "mechanism" is the one that separates a good write-up from a command log. Across the eleven lessons there are only a handful of underlying ideas, and you have met every one of them:

  • a credential that is guessable or shared
  • special authority held by an account that does not need it
  • public authority on an object that should be restricted
  • a way out of a restricted menu, or around a command line that was supposed to be limited
  • protection that does not travel with a copy
  • a program that adopts its owner's authority and trusts what the caller gives it
  • a name resolved by library list order, so whoever controls the order controls the result

For each lesson, pick the one that fits and say why. If two fit, say both. If none fit, you have found something worth writing up for its own sake.

5.7 Flags

Some lessons hide a flag, a string that looks like FLAG{...}, in the data the exploit reaches. Flags are how the range checks that you reached the data and did not just describe it. Every machine makes its own secret when it is set up, so your flags are yours alone, and a flag from a classmate's machine is no good on yours.

Write what you found into a text file, one lesson per line, in the form lesson-id = FLAG{...}, and check it:

./check-flags.sh submission.txt

Some lessons have no text to find. They are won by a change, such as a new profile with *ALLOBJ or a copy of a file that should not be readable, and those are checked from the saved state without any submission.

A flag is not the lesson. The flag shows that you reached the data. The write-up shows that you understand why you could.

5.8 The Write-Up

The deliverable for the course is a write-up covering the eleven lessons. For each one, give the reader four things: a short narrative of what you did, the evidence that proves it, the impact on the data in plain language, and the remediation in terms of what to change on a real system. Write it so that a manager and an auditor could both follow it, and include the exact commands.

It is graded out of 100:

PartPointsWhat earns full marks
Exploits executed30At least ten lessons run, each with the evidence and what it means for the data
Write-up quality25Narrative, evidence, impact and remediation for each, readable by a manager and an auditor
Remediation and mechanism25Every lesson names the mechanism and the fix, in terms of what to change on a real system
Secure range proof20Every exploit re-run after the fix, with where it stops recorded and why

Points come off for aiming anything at a real system instead of the range, for leaving out a statement of the authorised use rule, and for claiming an effect the simulator does not produce. Honest limits earn credit. Silverlake is a behavioural simulator, and some of its wording and rules come from IBM's documentation and not from a real system. A report that says where it is unsure beats one that pretends it is certain.

5.9 Tabletop: An Auditor Finds It in Production

Put the keyboard away for this one. Imagine an auditor has found a program like RUNCMD on a production system, one that hands a command to the system as its owner. Work through these questions in a group, out loud, before you write anything:

  • Who owns the program, and what authority does that owner hold?
  • Who is allowed to call it?
  • What is the first thing you would check on a real system, and what would you not touch until you had a copy of the evidence?
  • How would you know whether anyone had already used it?
  • What is the smallest change that stops the problem, and what would break if you made it today?

The last question is the hard one. A fix that breaks the nightly run gets reversed by Tuesday. A good remediation plan names its own risk.

5.10 Honest Limits

Everything in this session happens on the simulator, and the states it flips are the ones this range defines. A real system has more settings, more history and more people who depend on it staying as it is. Treat the loop as practice for the discipline: run it, name it, change one thing, prove it, and write it down. The habit transfers even where the screens do not.
