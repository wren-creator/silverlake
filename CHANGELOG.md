# Changelog

## Unreleased

- Work list options 2, 4 and 8. Option 2 on WRKOBJ and WRKOBJOWN opens the Edit Object Authority screen (EDTOBJAUT), laid out like the real one captured from PUB400: change an authority by retyping it, clear the field to remove a user (our reading), change the authorization list. Someone without `*OBJMGT` gets "Not authorized to change authorities." and no screen, as the real system did. Option 4 gathers every marked row onto a Confirm Delete screen (F12 keeps your options, Enter deletes) and runs DLTLIB, DLTF, DLTCMD, DLTMNU or DLTPGM with the authority each IBM page names. Option 8 shows Display Object Description (DSPOBJD). Creation date and time are blank because we keep none, and F6, F10 and F11 on the edit screen are not built. Two new oracle scenarios made this possible: `auth-objopts` (the one approved write, a throwaway QTEMP data area that is gone at sign-off) and `auth-edtautl`. Comparing against them also moved "Bottom" and "More..." to their real columns.

- `start.sh --port N` (or `-p N`) picks the port, and a port that is already taken is refused with a suggestion for the next one. The script also no longer says "up" after a one second sleep. It waits for the server's own "listening" line, so a crash during startup (a bad import, a taken port) now fails loudly with the log tail. This came from a cloned copy that crashed on import mid-refactor while `start.sh` reported success.

- Work list options. WRKOBJ, WRKOBJOWN and WRKAUTL are laid out like the real displays captured from PUB400 (option column, headers, the 73 long command line, key lines, the create row on WRKAUTL) and accept options: 5 on objects and owners shows authority, 7 renames and 13 changes the description (the new name or text goes on the command line, as the real display says), 9 on WRKOBJOWN changes the owner, 5 and 8 on WRKAUTL display the list or the objects it secures, and 1 on the create row makes a list. Each option runs the matching command, so it needs `*USE` to that command, and Enter or F3 comes back to the list. New commands RNMOBJ and CHGOBJD follow IBM's pages (`*OBJMGT` on the object and `*UPD` plus `*EXECUTE` on the library to rename; renaming a library takes its contents and the profiles that point at it). Options 2, 4 and 8 came in the next entry; 3 on objects, and 2, 4, 9, 13 on lists say they are not available yet. A `compare` of the new WRKOBJ screen against the real capture reports no field differences.

- Oracle: `auth-objects`, a read-only scenario for WRKOBJ, WRKOBJOWN, WRKAUTL and DSPAUTL, run against PUB400 with the test profile. It corrected three things. After sign-on a real message line shows the text alone, with no message ID in front (Silverlake printed it). A real basic profile sees authorization lists through public authority, not only by owning one or holding an entry. And the real Display Authorization List has its own layout (User, Object Authority, List Mgt columns), which Silverlake now follows. The capture also recorded the options the real WRKOBJ, WRKOBJOWN and WRKAUTL displays offer, which the command pages never listed; building them is on the roadmap.

- Phase 3c-3b, finding and owning objects: WRKOBJ (generic names, `*ALL`, and the library values `*LIBL` `*CURLIB` `*USRLIBL` `*ALLUSR` `*ALL`), WRKOBJOWN and CHGOBJOWN. Lists show only libraries you can use and objects you have some authority to, so a locked library hides its contents even when the files are wide open. CHGOBJOWN follows the page: `*OBJEXIST` on the object, `*ADD` to the new owner, `*DLT` to the old one, `*ALLOBJ` skips the checks, and `CUROWNAUT(*SAME)` keeps the old owner as a private entry. The pages do not list the options on these displays, so the lists are view only for now.

- Phase 3c-3, authorization lists: CRTAUTL, DLTAUTL, ADDAUTLE, CHGAUTLE, RMVAUTLE, DSPAUTL and WRKAUTL from IBM's 7.5 command pages, with the documented message IDs (CPF2278, CPF2279, CPF2280 to CPF2290, CPF22AA to CPF22AC and the rest). Lists now have an owner and text, and `*AUTLMGT` exists as an authority that is not part of `*ALL`. The new rules worth knowing: `*PUBLIC` is always on a list and can never manage it, only the owner or `*ALLOBJ` can hand out `*AUTLMGT`, a `*AUTLMGT` user can only deal in authorities they hold, and a list that secures an object cannot be deleted. The state file upgrades itself, and the seven commands are `*CMD` objects like the rest. The page text for what happens to objects when a list goes away is silent, so Silverlake refuses the delete, as the page says. Several rules are inferred and flagged in docs/access-model.md.

- Phase 3c-2, menus and limited capabilities. A job now lands on a `*MENU` object laid out like the real MAIN menu captured from PUB400 (command line at row 19, column 6, 153 long, not monocase), where the old placeholder screen sat. `GO` has the ten deep menu stack, F12 and F3 return points, and `RTNPNT` from IBM's page; F3 on the initial menu does nothing, as on the real system. The sign-on screen's program, menu and library fields are honored, `INLMNU(*SIGNOFF)` signs off, and `LMTCPB` follows IBM's text (CPF2294, CPF2295 and CPF2297 on `CHGPRF`, a refusal at sign-on, no command line for `*YES`). `CALL QCMD` opens command entry. New seed profile `CLERK` is limited, but its menu has a `CALL QCMD` option, so the escape from limited capabilities can be practiced, and `RVKOBJAUT` on `QSYS/QCMD` closes it. Writing the tests found that `RTNPNT` bound to a boolean, so `GO` never recorded a return point. Programs other than `QCMD` are not modeled, and the wording a limited user sees at a command line is not documented, so it is ours.

- Commands are objects. Every command is a `*CMD` object in QSYS, running one takes `*USE` to it before its parameters are read, and a refusal says `Not authorized to command X in library *LIBL.`, the wording a real system gave a basic profile on PUB400. The seed is permissive, so a site policy like PUB400's is one `RVKOBJAUT OBJ(QSYS/CRTLIB) OBJTYPE(*CMD) USER(*PUBLIC) AUT(*USE)` away, and `GRTOBJAUT` reopens it for one user or group. Objects gained a `data` field for type-specific content, and the state file upgrades itself from the older layout. `*CMD`, `*MENU` and `*PGM` are valid object types for `DSPOBJAUT`, `GRTOBJAUT` and `RVKOBJAUT`.

- Oracle: `auth-crtlib`, the only scenario that changes a host. It creates a throwaway library with a fresh random name (the environment cannot choose it), looks at its authority, deletes it, and signs off, and it skips straight to sign-off unless the host says the library was created. Its first real run was refused with `Not authorized to command CRTLIB in library *LIBL.`, which settled the `CRTLIB` question differently than expected: the gate is authority to the command, itself an object, not authority to QSYS. Nothing was created. Tests cover the create-gate, the name override, and the local create, inspect, delete, sign-off round trip.

- First real authenticated captures (a test profile on PUB400, over TLS, read-only) changed the model. `QSYS` is public `*USE` and `QGPL` public `*CHANGE`, both owned by a new `QSYS` profile; the default library list is now `QSYS QSYS2 QUSRSYS QHLPSYS`, current library, `QGPL QTEMP`; and `DSPOBJAUT` shows a basic user one `*PUBLIC` row when they have no entry of their own. The invented rule that `CRTLIB` needs `*ADD` to QSYS is gone, because a real QSYS has no public `*ADD`. The first run also showed that F3 on the real main menu does not sign off and leaves a disconnected job, so every scenario now ends with `SIGNOFF`.

- Oracle: authenticated captures. The oracle can sign on as a test profile with credentials from a gitignored, mode-600 `.env` (only `SILVERLAKE_ORACLE_*` names, never echoed). New `--tls` option verifies the certificate and host name with no way to switch that off, and a scenario that sends a password refuses cleartext beyond loopback. Values are resolved before connecting, a refused sign-on stops the run after one attempt, and the two new scenarios (`auth-probe`, `auth-libs`) only run `DSPLIBL` and `DSPOBJAUT`. `compare` replays an authenticated capture locally as a seed profile. Writing the test for the stop rule found that the first version, keyed on the terminal's error line, never fired on a real refusal, so it now looks for a message ID or a remaining password prompt.

- Phase 3c-1, commands: CRTLIB, DLTLIB, DSPLIBL, ADDLIBLE, RMVLIBLE, WRKLIB, DSPOBJAUT, GRTOBJAUT and RVKOBJAUT, built from IBM's 7.5 command pages. Each job has its own library list, and unqualified names are found through it. Revoking everything from a user removes the entry so they fall through to groups and public, which is different from holding `*EXCLUDE`. The message ladder (library not found, library locked, object not found, no authority) lets a low-authority user map what exists, on purpose. Qualified names, `*LIB` and `*FILE` objects, and single explicit names only for now. Seed `QSYS` public authority is `*CHANGE` so anyone can `CRTLIB`; that rule is inferred and flagged.

- Phase 3c-1, object model: objects are identified by library, name and type, libraries are `*LIB` objects in QSYS, and authority to an object now includes the library gate (`*EXECUTE` on the library first, `*ALLOBJ` skips it). The seed gains six libraries and three files, including `SRCLIB/QRPGSRC`, a wide open file in a locked library. Libraries, objects and authorization lists moved from one JSON row to real SQLite tables, and the seed is validated (library, owner and authorization list must exist). Deleting a profile with `OWNOBJOPT(*DLT)` takes a deleted library's contents with it.

- Phase 3b: manage users from inside a session. CRTUSRPRF, CHGUSRPRF, DSPUSRPRF, DLTUSRPRF, WRKUSRPRF and SIGNOFF work from a command line, following the IBM i 7.5 command reference: `*SECADM` to create or change, only authorities you hold can be given, `*SECADM` and `*AUDIT` need `*ALLOBJ` too. Profiles are secured objects with an owner, so a `*SECADM` user can only touch profiles they own or hold authority to, which is why `DEVADMIN` cannot change the seeded accounts. Deleting handles owned objects (`OWNOBJOPT`), group cleanup, and refuses protected or in-use profiles. Changes persist in `state/silverlake.sqlite`, and `reset.sh` wipes them. Message IDs for these commands come from IBM's lists and are marked as documented, not seen. Sessions are counted in and out, including dropped connections.

- Phase 3a: the access model. Five user classes with IBM's defaults by QSECURITY level, eight special authorities, grant rules, object authority with `*ALL`/`*CHANGE`/`*USE`/`*EXCLUDE`, authorization lists and groups. Profiles come from `data/profiles.toml` (19 seed accounts, one per class, one per special authority, plus the usual misconfigurations). Sign-on now checks the profile and answers with message IDs. A placeholder menu shows the effective access after sign-on. Found live: a profile with all eight authorities overflowed the screen and dropped the session; screens now wrap, and a failing session is logged without touching others.
- Sign-on screen moved to the stock layout, taken from a photo of a default display and the stock parts of the PUB400 capture: fields at col 52 on rows 5 to 9, info block at cols 47 and 69 on rows 1 to 3, copyright at col 39, no date line. The message-on-bottom-row behavior is unchanged.
- Phase 2: fidelity oracle. A 5250 client, host stream decoder, structural diff, and a CLI (`python -m silverlake.oracle`) with an allowlist and rate limit for non-loopback hosts. First captures from PUB400 fed back three generic fixes: monocase on the sign-on user field, fields that wrap across rows, and the bottom-row message line. Snapshots are re-derived from raw records so old captures stay comparable.
- Phase 1: 5250 core. Telnet framing, TN5250E negotiation (terminal type, NEW-ENVIRON device name, binary, EOR), GDS records, declarative screens rendered to a real data stream, sign-on screen that round-trips. Checked against web3270's tn5250 client.
- Repo scaffold: README, ROADMAP, architecture and not-faked docs, lifecycle scripts, loopback guard.
