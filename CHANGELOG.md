# Changelog

## Unreleased

- FTP on 127.0.0.1:2121 with the other services. Sign-on goes through the profile store (clear text, bad attempts count), `RETR` and `LIST` obey the same file authority as DSPPFM, and both naming formats work. Read only: nothing can be written, deleted or made. No lesson on it yet.

- Network services, first one. `./start.sh --services` (or `SILVERLAKE_SERVICES=1`) now also starts the HTTP Server Administration console on 127.0.0.1:2001, in the same process as the 5250 server, so it signs in against the same profiles and sees lesson toggles at once. A new lesson group D and lesson `httpadmin-ssi-injection`: the Create HTTP Server description is evaluated for `exec` directives and the command runs as QTMHHTTP, so an ordinary profile reads a system profile's message queue (the flag) that the 5250 side refuses it. The command goes to Silverlake's own dispatcher, never a shell. The secure state records the fix PTF on `QHTTPSVR/QZHBADMIN` and the field is escaped. IBM has not published the real parameter, so this models the bug class, not the bug. `scenario.sh` keeps services on across its restart. Details in docs/services.md. FTP and the host servers are the next two steps.

- Instructor kit, in the shape of Cross Creek's. `instructor/` holds a two day agenda, an answer key with the teaching notes and a one line mechanism and fix for every lesson, a capstone rubric, a setup runbook (including why flags differ per machine and how to score on the student's own), and five session decks: orientation, one each for the three lesson groups, and fix and re-run. A test keeps the answer key and the registry in step.

- An exploit test for every lesson. `tests/test_exploits.py` plays each lesson's steps from docs/scenarios.md through the 5250 screens and commands, and checks the flag: it has to win against the vulnerable range and fail once the lesson is set to secure. The vulnerable half also proves the exploit itself still works, so a broken exploit cannot make the fixed half pass for nothing. A test fails if a lesson has no exploit there.

- Scenario docs, generated. Each lesson file now carries its own prose (where, real-world parallel, vulnerability, MITRE ATT&CK, exploit steps, consequence, fix, reference) in a `[doc]` block next to the changes it describes, and `python -m silverlake.scenario_docs` writes `docs/scenarios.md` (instructor, with fixes) and `docs/scenarios-trainee.md` (the same without them) from the registry. A test fails if either file is out of date or a lesson is missing a field. The exploit steps use the commands the tests run; the real-world parallels are general patterns, not named incidents.

- Flags. Every range has an instance secret (`.instance-secret` at the repo root, made by `setup.sh`, never committed and untouched by `reset.sh`), and each lesson's flag is `FLAG{...}` derived from it, so flags differ between ranges, cannot be guessed from the repo and are the same after a reset. Seven lessons plant theirs where the exploit reaches (the security officer's job log, a vault file only `*ALLOBJ` reads, maintenance notes only the clerk may read and only from a command line, the operator's message queue, the payroll register on QPRINT, a report heading, an audit employee in the payroll file) and four are scored from the saved state (a new profile with `*ALLOBJ`, employee 10004's salary at 99999, STUDENT able to read PAYROLL, a readable copy of PAYROLL). `./check-flags.sh submission.txt` scores a trainee with the server running, and `--show` gives the instructor every flag, state check and the secure-state passwords, which also come from the secret now. The seed carries `@@FLAG:id@@` where a flag goes and the loader fills it in. PAYROLL has a seventh record, so totals moved by one.

- Scenarios, the switch between a vulnerable and a secure range. Eleven lessons are now files in `data/scenarios/`, in three groups (credentials and recon, authority and data exposure, programs and the library list), each listing what its fix changes with both the vulnerable and the secure value of every field. `./scenario.sh list`, `show`, `set <id> vulnerable|secure`, `reset <id>` and `mode vulnerable|secure` change the saved state with the server stopped and start it again (anyone signed on is signed off). `reset` puts a lesson back to vulnerable and clears what its exploit left: restored files, copies it made, profiles it created, spooled reports. The state of every lesson is saved with the rest. A library can now have a CRTAUT (`data.crtaut`) that new files get instead of the library's public authority, which is the fix for the CPYF copy. Tests check that every vulnerable value is what the seed really holds, so a lesson cannot drift from the range. Not yet: flags, generated scenario docs and the exploit-versus-fix test for every lesson (5b to 5d), and a live toggle without a restart.

- F4 prompts for the five compile and create commands. Type `CRTBNDRPG`, `CRTPF`, `CRTDSPF`, `CRTPRTF` or `CRTSRCPF` on any command line, in PDM too, press F4, and the prompt comes up on the layout captured from PUB400: the same rows, labels and columns, Bottom marker and key lines, "Parameter FILE required." and "Already at bottom of area." Whatever was typed fills the fields, F4 beside option 14 in Work with Members prompts the compile for that member with its name filled in, and Enter runs the command line the fields make. RCDLEN on CRTPF and SRCSTMF on CRTBNDRPG are drawn and refused, because those compiles are not built. F10, F13 and F24 say they are not built. Where the captured host offered `*NONE` for SRCFILE the field holds QDDSSRC, so Enter works.

- CPYF and DSPPFM. `CPYF` copies records between physical files with MBROPT (`*NONE`, `*ADD`, `*REPLACE`, `*UPDADD`), CRTFILE, FMTOPT, FROMRCD and NBRRCDS, and asks for `*USE` on the from-file and `*ADD` (plus `*DLT` or `*UPD`) on the to-file. The point for the range: a file CPYF creates belongs to whoever copied and is not on the original's authorization list, so `*USE` on a locked file is enough to walk out with an unlocked copy, and one made in QTEMP is gone at sign-off. `DSPPFM` shows a file's records as raw characters to anyone with `*USE`, with Control, Roll and F19/F20. None of it was captured from a real system, so authority is from IBM's pages as remembered and wording and layout are ours. Not built: CPYSRCF, source files in CPYF, F10/F11/F21 and Find in DSPPFM.

- Overrides and a QTEMP of your own. `OVRDBF` and `DLTOVR` redirect the file a program opens, with `SECURE(*YES)` honoured, and the open is checked as whoever the call stack holds, so an adopting program opens the caller's choice with its owner's authority. QTEMP is now per job: what a job makes there is invisible to the others and gone at sign-off, and it sits ahead of a library added with `ADDLIBLE ... *LAST`, so a program of your own in QTEMP runs in place of one an adopting program calls by name. Seeded to practise on, each with its fix: `EMPDIR` and `EMPDIRX` (redirect a public directory to the payroll file, fixed by giving the program an owner who cannot reach payroll) and `PAYRUN` and `PAYRUNX` (hijack `PAYCALC` through QTEMP, fixed by calling `APPLIB/PAYCALC`). OVRSCOPE all acts as `*JOB`, and listings do not hide other jobs' QTEMP objects yet. Both lessons are in docs/rpg.md.

- PDM and a source editor, so a program can be typed in, compiled and run without leaving the 5250. `STRPDM` shows the captured menu, `WRKMBRPDM` lists the members of a source file with options to edit, copy, delete, browse, rename, change text and compile (the member type picks CRTBNDRPG, CRTPF, CRTDSPF or CRTPRTF), and `STRSEU` opens the editor directly. The editor has the line commands I, D, C, M and R with counts, DD, CC, MM and RR blocks, A and B targets, FIND, CHANGE, SAVE, FILE, CANCEL and an exit display on F3. A member is locked while it is open, editing needs authority to the file and browsing only needs to read it. The refusals use the PUB400 wording (a library that is not there, no authority to the file). The Work with Members and editor screens are ours, and so are the plain line numbers where SEU has `NNNN.00` and dates. Not built: the PDM prompts for options 1, 2 and 3, syntax prompts, column shift and the F4 prompts.

- The compile workflow, first half. `CRTSRCPF` makes a source file, `CRTBNDRPG` compiles a member of one into a `*PGM`, and `CRTPF`, `CRTDSPF` and `CRTPRTF` build a file from a DDS member, all checked by the runtime and each leaving a compile listing on the spool as QSYSPRT. A compile fails when the source has a syntax error or the program declares a file that is not on the library list, and says so in the listing. A program that is replaced belongs to the user who compiled it, which is also why compiling an `*OWNER` program yourself only adopts you. `SRCLIB` gets `QRPGLESRC` and `QDDSSRC` with HELLO, HELLOD and CUSTPF to practise on. The wording for a member that cannot be opened, and the layouts and defaults of the five prompts, come from a read-only PUB400 capture (`auth-pdm`, which also captured the PDM menu and its refusals for the next piece). The completion messages and the listing are ours. Not built yet: the F4 prompts, PDM and the editor, so there is no way to type a new member in yet.

- Display files are objects. A program's `WORKSTN` file is now a `*FILE` of type DSPF that carries the DDS, found by the F-spec name through the library list and needing `*USE`, so two programs can share one screen layout (RUNCMD and RUNCMDX do) and a change to the file changes the screen for both. A program that still carries its DDS inline keeps working when no such file is on the list. After the list the program's own library is tried, a deliberate simplification so `CALL APPLIB/ADVENTURE` works without ADDLIBLE first. Seeded: SCREEN, REPORT, EMPINQ, SALADJ and RUNCMD in APPLIB.

- Printer files. A program that declares a `PRINTER` file prints through a `*FILE` object that carries the printer DDS and the queue it goes to (QPRINT unless it says otherwise), and what it writes becomes a spooled file of the job on that queue, owned by the user running it and not by an owner the program adopts, with the next file number in the job. Using the printer file needs `*USE` and the queue `*READ`, checked as whoever the call stack holds. The point is who can read the result: `REGRPT` prints the payroll register to QPRINT, where anyone can open it, and `REGRPTX` prints it to a queue that shows contents only to the owner. The fix is the printer file's queue. Output is updated after every screen, so a program that stops half way leaves what it printed. Not built: CHGPRTF, OVRPRTF, copies and page size from the file.

- DISK files for RPG programs. A `*FILE` object can now carry a record layout (DDS) and records, and a program that declares a file in an F-spec reads and writes them, with the file found through the library list. Opening needs `*OBJOPR` plus the right for the mode (`*READ`, `*UPD`, `*ADD`) and each read, add, update and delete is checked again, against whoever the call stack holds at that moment, so adopted authority reaches a file the user cannot and stops when the program does. Writes go back into the object after every screen. Seeded: `APPLIB/PAYROLL` (locked to payroll staff by an authorization list) and `CUSTOMERS` with records, `PAYLOOK`, which adopts a reader so anyone can look an employee up, and `PAYADJ`, which adopts an owner who can change everything and checks nothing, so anyone who may call it can set anyone's salary. The fix for that one is on the program's own authority. rpgle_library gained an `authorize` hook on its database, `load_rows` and `dump_rows`, and puts a program on the stack before its files open (db7c4c1, aa4b2f9). Not built: printer files, DSPF objects, logical files, OVRDBF, file commands.

- Adopted authority and QCMDEXC. A program with `USRPRF(*OWNER)` now runs with its owner's authority added to the caller's, special authorities included, for as long as it is on the call stack. `USEADPAUT` decides whether what the program before it held passes down, and the job log says which owner a program ran as. `CALL 'QCMDEXC'` runs a CL string through Silverlake's own dispatcher as the profile the stack holds, never through a shell, with the captured wording for an unknown command and a command cut short. Two programs are seeded in APPLIB: `RUNCMD`, a QSECOFR-owned helper that passes whatever is typed to QCMDEXC and so lets a basic user create a security officer, and `RUNCMDX`, the fix, which has an allow-list and an owner with no authority. A group profile assignment in CRTUSRPRF still needs the caller's own authority, as IBM says. rpgle_library gained `ProgramLoader.active` (e2f8612). Unconfirmed: that the owner's special authorities pass, and how a real program sees a failed QCMDEXC. Both are on the verification list.

- RPG programs run. `CALL PGM(APPLIB/ADVENTURE)` starts a `*PGM` object that carries RPG IV source and the DDS of its display file, on the rpgle_library interpreter, and every `EXFMT` becomes a screen on the 5250 until the program ends. A function key goes to the program only if its display file named it, a letter in a number field is refused the way a real keyboard would, one program can call another through the caller's library list and authority, and a program that runs 200,000 instructions without a screen is stopped, because the interpreter shares the server's thread and one `DOW` would freeze every session. `DSPPGM` shows the program's owner, attribute and the two lines that matter, user profile and use adopted authority, laid out from a PUB400 capture of the system's own QCMDEXC. A CALL on a program that is not there says what the real host says. Two seeded programs are in APPLIB. Not built yet, and the next milestone: acting on adopted authority, `QCMDEXC`, files and a compile step. The library gained a step cap, host-answered programs and a `name_for` hook for this (rpgle_library 6364452).

- Sign-on follow-ups. CHGPWD changes your own password, and the Change Password display, CHGPWD, CRTUSRPRF and CHGUSRPRF all now answer to the password rules: minimum and maximum length, a required digit, no adjacent digits, no repeated characters, and a remembered history of old passwords (QPWDRQDDIF). PWDEXPITV on a profile overrides the system interval, and within QPWDEXPWRN days of expiry the first screen says how long is left. The seed keeps the rules loose so there is something to tighten. Wording is ours and sits on the verification list. I left out a warning before the last bad attempt: I do not believe the real host sends one, and inventing it would teach people something false. Also fixed: a NEWPASSWORD2 value was not masked in job logs.

- The other spooled file options, on WRKSPLF and WRKOUTQ, from a read-only capture that opened each prompt and backed out. Option 1 opens Send Network Spooled File and says nothing can be sent, option 2 opens Change Spooled File Attributes and applies copies and form type through a new CHGSPLFA command (moving it to another queue needs read authority to the target, and the control rule is the same as hold and delete), option 7 says there are no messages for the file, and option 9 opens Work with Printing Status, which reports the file is not on a started printer because no printer exists. Option 4 deletes straight away: the real confirm was never captured, because the oracle will not press 4. - CRTOUTQ and DLTOUTQ, from IBM's two pages. A new queue is owned by its creator with AUT defaulting to `*USE` (the page's default, unlike CRTMSGQ), and DSPDTA, OPRCTL and AUTCHK are stored. DLTOUTQ refuses a queue that still holds files, and needs `*OBJEXIST`, which `*USE` and `*CHANGE` do not have, so the owner is the only one who can delete a queue made with the defaults. The CRTOUTQ page has no restrictions section and DLTOUTQ names no authority, so those parts are inferred and on the verification list. WRKOBJ option 4 on a queue runs DLTOUTQ.

- WRKOUTQ, from the two PUB400 captures. `WRKOUTQ OUTQ(QGPL/QPRINT)` lists a queue's files in the real layout, and options 3, 5, 6 and 8 work like they do on WRKSPLF. The teaching point is the capture's: reading a queue shows you every file on it, owner and job name included, and the queue's display rule only hides the contents, so a basic profile can list who has been running what from the job log queue. A queue or library that does not exist gets one message for both, as the real host did. The bare WRKOUTQ (every queue on the host) says it is not built. Not drawn: F11 view 2, F20, F22, F24, because none is built.

- CRTMSGQ, CHGMSGQ and DLTMSGQ, built from IBM's command pages. A new queue is delivery *HOLD, severity 00, owned by its creator, and AUT sets who else can touch it. CHGMSGQ needs *USE and *DLT on the queue, DLTMSGQ needs *OBJEXIST on top, so the default *CHANGE lets anyone write to a queue and change it but not delete it. QSYSOPR cannot be deleted. WRKOBJ option 4 on a queue runs DLTMSGQ.

- DSPJOBLOG and WRKJOB, from a read-only capture of the real displays. DSPJOBLOG shows the live log of a job, commands as `3>> COMMAND` and what they raised, the command itself last, so a session can read another session's log as it happens. The rule is quoted from IBM's page: `*JOBCTL` or the job's own user, and a job that has `*ALLOBJ` needs `*ALLOBJ` to read (JOBMAN reads a plain user's log and not QSECOFR's). The refusal is CPF2441. WRKJOB is the Work with Job menu, with option 4 (spool files), 10 (the log) and 13 (your library list) working, and it is behind WRKACTJOB option 5. Fixed on the way: F12 on a list opened from another screen went all the way to the menu, and now goes back one level.

- Job control. HLDJOB, RLSJOB, ENDJOB and CHGJOB work, behind WRKACTJOB options 3, 6, 4 and 2. The rule is quoted from IBM's pages: you run under the job's own profile, or you hold `*JOBCTL`, and neither `*SPLCTL` nor `*ALLOBJ` alone will do (a test pins that). `CHGJOB` takes JOBPTY, OUTPTY, RUNPTY, TIMESLICE, PURGE, DFTWAIT, CPUTIME and MAXTMPSTG, and the last six need `*JOBCTL` even on your own job. Values are stored and shown, nothing is scheduled. ENDJOB on another session works: that session notices on its next key, files its job log and lands on sign-on. Ending a seeded system job removes it until a restart. Option 4 has no confirm screen and option 2 takes its attributes from the command line, because neither real screen was captured. The ID for each refusal is from the pages, which condition raises it is inferred.

- Phase 3c-3c step 3, message queues, which finishes jobs, spool and messages. DSPMSG, SNDMSG and CLRMSGQ work, with the Display Messages screen laid out from two PUB400 captures (a user queue and QSYSOPR). Queues are `*MSGQ` objects, so the authority commands work on them, messages are saved with the state, and every profile has a queue in QUSRSYS made on first use and removed with the profile. The rules come from IBM's pages (SNDMSG needs `*OBJOPR` and `*ADD`, CLRMSGQ needs `*CHANGE`); DSPMSG's page has no authority section, so needing `*USE` is inferred and fits the capture. What the capture showed is the point: a basic profile can read QSYSOPR and learn other people's job names from it. Silverlake seeds QSYSOPR public `*CHANGE` and QUSRSYS public `*CHANGE`, so by default anyone reads and writes anyone's queue, and revoking public authority gives CPF2408. Delivery and severity are shown, not acted on; inquiry messages, replies, F11 and a real SNDMSG prompt are not built (the real prompt got no answer when captured). Docs in docs/jobs-spool-messages.md.

The capture also recorded the options the real WRKOBJ, WRKOBJOWN and WRKAUTL displays offer, which the command pages never listed; building them is on the roadmap.

- Phase 3c-3b, finding and owning objects: WRKOBJ (generic names, `*ALL`, and the library values `*LIBL` `*CURLIB` `*USRLIBL` `*ALLUSR` `*ALL`), WRKOBJOWN and CHGOBJOWN. Lists show only libraries you can use and objects you have some authority to, so a locked library hides its contents even when the files are wide open. CHGOBJOWN follows the page: `*OBJEXIST` on the object, `*ADD` to the new owner, `*DLT` to the old one, `*ALLOBJ` skips the checks, and `CUROWNAUT(*SAME)` keeps the old owner as a private entry. The pages do not list the options on these displays, so the lists are view only for now.

- Phase 3c-3, authorization lists: CRTAUTL, DLTAUTL, ADDAUTLE, CHGAUTLE, RMVAUTLE, DSPAUTL and WRKAUTL from IBM's 7.5 command pages, with the documented message IDs (CPF2278, CPF2279, CPF2280 to CPF2290, CPF22AA to CPF22AC and the rest). Lists now have an owner and text, and `*AUTLMGT` exists as an authority that is not part of `*ALL`. The new rules worth knowing: `*PUBLIC` is always on a list and can never manage it, only the owner or `*ALLOBJ` can hand out `*AUTLMGT`, a `*AUTLMGT` user can only deal in authorities they hold, and a list that secures an object cannot be deleted. The state file upgrades itself, and the seven commands are `*CMD` objects like the rest. The page text for what happens to objects when a list goes away is silent, so Silverlake refuses the delete, as the page says. Several rules are inferred and flagged in docs/access-model.md.

- Phase 3c-2, menus and limited capabilities. A job now lands on a `*MENU` object laid out like the real MAIN menu captured from PUB400 (command line at row 19, column 6, 153 long, not monocase), where the old placeholder screen sat. `GO` has the ten deep menu stack, F12 and F3 return points, and `RTNPNT` from IBM's page; F3 on the initial menu does nothing, as on the real system. The sign-on screen's program, menu and library fields are honored, `INLMNU(*SIGNOFF)` signs off, and `LMTCPB` follows IBM's text (CPF2294, CPF2295 and CPF2297 on `CHGPRF`, a refusal at sign-on, no command line for `*YES`). `CALL QCMD` opens command entry. New seed profile `CLERK` is limited, but its menu has a `CALL QCMD` option, so the escape from limited capabilities can be practiced, and `RVKOBJAUT` on `QSYS/QCMD` closes it. Writing the tests found that `RTNPNT` bound to a boolean, so `GO` never recorded a return point. Programs other than `QCMD` are not modeled, and the wording a limited user sees at a command line is not documented, so it is ours.

- Commands are objects. Every command is a `*CMD` object in QSYS, running one takes `*USE` to it before its parameters are read, and a refusal says `Not authorized to command X in library *LIBL.`, the wording a real system gave a basic profile on PUB400. The seed is permissive, so a site policy like PUB400's is one `RVKOBJAUT OBJ(QSYS/CRTLIB) OBJTYPE(*CMD) USER(*PUBLIC) AUT(*USE)` away, and `GRTOBJAUT` reopens it for one user or group. Objects gained a `data` field for type-specific content, and the state file upgrades itself from the older layout. `*CMD`, `*MENU` and `*PGM` are valid object types for `DSPOBJAUT`, `GRTOBJAUT` and `RVKOBJAUT`.

- Oracle: `auth-crtlib`, the only scenario that changes a host. It creates a throwaway library with a fresh random name (the environment cannot choose it), looks at its authority, deletes it, and signs off, and it skips straight to sign-off unless the host says the library was created. Its first real run was refused with `Not authorized to command CRTLIB in library *LIBL.`, which settled the `CRTLIB` question differently than expected: the gate is authority to the command, itself an object, not authority to QSYS. Nothing was created. Tests cover the create-gate, the name override, and the local create, inspect, delete, sign-off round trip.

- First real authenticated captures (a test profile on PUB400, over TLS, read-only) changed the model. `QSYS` is public `*USE` and `QGPL` public `*CHANGE`, both owned by a new `QSYS` profile; the default library list is now `QSYS QSYS2 QUSRSYS QHLPSYS`, current library, `QGPL QTEMP`; and `DSPOBJAUT` shows a basic user one `*PUBLIC` row when they have no entry of their own. - Phase 3c-1, commands: CRTLIB, DLTLIB, DSPLIBL, ADDLIBLE, RMVLIBLE, WRKLIB, DSPOBJAUT, GRTOBJAUT and RVKOBJAUT, built from IBM's 7.5 command pages. Each job has its own library list, and unqualified names are found through it. Revoking everything from a user removes the entry so they fall through to groups and public, which is different from holding `*EXCLUDE`. The message ladder (library not found, library locked, object not found, no authority) lets a low-authority user map what exists, on purpose. Qualified names, `*LIB` and `*FILE` objects, and single explicit names only for now. Seed `QSYS` public authority is `*CHANGE` so anyone can `CRTLIB`; that rule is inferred and flagged.

- Phase 3c-1, object model: objects are identified by library, name and type, libraries are `*LIB` objects in QSYS, and authority to an object now includes the library gate (`*EXECUTE` on the library first, `*ALLOBJ` skips it). The seed gains six libraries and three files, including `SRCLIB/QRPGSRC`, a wide open file in a locked library. Libraries, objects and authorization lists moved from one JSON row to real SQLite tables, and the seed is validated (library, owner and authorization list must exist). Deleting a profile with `OWNOBJOPT(*DLT)` takes a deleted library's contents with it.

- Phase 3b: manage users from inside a session. CRTUSRPRF, CHGUSRPRF, DSPUSRPRF, DLTUSRPRF, WRKUSRPRF and SIGNOFF work from a command line, following the IBM i 7.5 command reference: `*SECADM` to create or change, only authorities you hold can be given, `*SECADM` and `*AUDIT` need `*ALLOBJ` too. Profiles are secured objects with an owner, so a `*SECADM` user can only touch profiles they own or hold authority to, which is why `DEVADMIN` cannot change the seeded accounts. Deleting handles owned objects (`OWNOBJOPT`), group cleanup, and refuses protected or in-use profiles. Changes persist in `state/silverlake.sqlite`, and `reset.sh` wipes them. Message IDs for these commands come from IBM's lists and are marked as documented, not seen. Sessions are counted in and out, including dropped connections.
